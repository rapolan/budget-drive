# Budget Drive Protocol (BDP) - Technical Architecture

**Version:** 2.2  
**Last Updated:** August 2026  
**Status:** Authoritative Technical Reference

---

## 1. System Overview

BDP is a multi-tenant driving school management platform designed with a **Hybrid Data Layer**. It balances operational performance and privacy with blockchain-backed immutability and auditability.

### Core Tech Stack
- **Frontend:** React 18, TypeScript, Vite, Tailwind CSS
- **Backend:** Node.js 18, Express, TypeScript
- **Primary DB:** PostgreSQL 14 (Multi-tenant operational data)
- **Overlay DB:** MongoDB (Indexed blockchain data for AI/Third-party queries)
- **Blockchain:** BSV (Overlay Services architecture via `@bsv/sdk` and `@bsv/overlay-express`)

---

## 2. The Hybrid Data Layer

BDP uses a Three-Layer Architecture to manage data based on privacy, speed, and audit requirements.

| Layer | Technology | Purpose | Key Data |
|-------|------------|---------|----------|
| **Operational** | PostgreSQL | Fast queries, PII protection | Student names, addresses, performance notes, real-time schedule state. |
| **Audit/Financial** | BSV Blockchain | Immutable truth, timestamps | Booking hashes, payment proofs, Merkle proofs, certificates, protocol fees. |
| **Overlay Index** | MongoDB | Queryable audit trail | Indexed hashes, SPV proofs, aggregated stats for AI agents/DMV. |

### Data Sovereignty Framework
We follow a strict "Where Does This Data Go?" decision tree:
- **Financial/Payment?** → Blockchain + MongoDB index.
- **Provable/Verifiable?** → Hash on Blockchain, full data in PostgreSQL.
- **Personal Identifiable Info (PII)?** → PostgreSQL only (Private).
- **High-Volume Operational?** → PostgreSQL (Fast).

---

## 3. BSV Standards & Protocols

BDP adheres to modern BRC standards to ensure interoperability within the BSV ecosystem.

### Key Standards
- **BRC-100:** Unified Wallet-to-Application Interface. Used for user auth and transaction signing.
- **BRC-52:** Identity & Verifiable Credentials. Used for instructor licenses and course completion certificates.
- **BRC-22 (SHIP):** Synchronizes Hosting for Indexing Peers. Broadcasts transactions to overlay hosts.
- **BRC-24 (SLAP):** Service Lookup Availability Protocol. Discovers available lookup services.
- **BEEF:** Background Evaluation Extended Format. The standard transaction envelope format.

### Protocol Prefixes & Fees
| Prefix | Action | Fee (sats) |
|--------|--------|------------|
| `BDP_BOOK` | Lesson Booking | 5 |
| `BDP_PAY` | Payment Record | 3 |
| `BDP_CERT` | Certificate Issuance | 10 |
| `BDP_NOTIFY` | Notification Sent | 1 |
| `BDP_PROGRESS`| Student Milestone | 2 |

## 4. Overlay Services Architecture

The "Overlay" consists of **Topic Managers** (admittance) and **Lookup Services** (indexing/querying).

### Topic Managers (Validation)
Decide which transaction outputs enter the overlay.
- **`tm_bdp_lessons`**: Validates `BDP_BOOK` structure (tenantId, studentHash, fee >= 5 sats).
- **`tm_bdp_payments`**: Validates `BDP_PAY` structure (amount, currency, fee >= 3 sats).
- **`tm_bdp_certs`**: Validates BRC-52 certificate signatures and protocol fees.

### Lookup Services (Querying)
Answer queries about the admitted data.
- **`ls_bdp_lessons`**: Queries lessons by `studentHash`, `instructorHash`, or `date_range`.
- **`ls_bdp_payments`**: Queries financial history and payment proofs.

## 5. Security & Privacy

### Hashing Strategy
To maintain student privacy while providing a public audit trail, we use sha256 hashes for identifiers on-chain:
- **`blockchain_student_hash`**: `sha256(student_id + salt)`
- **`blockchain_lesson_hash`**: `sha256(lesson_id + start_time + parties)`

### Role-Based Access Control (RBAC)
- **Owners:** Full access to multi-tenant school settings and financial data.
- **Instructors:** Access restricted to their own schedules, students, and earnings.
- **Staff:** Configurable access to operational data (Students/Vehicles).

## 6. Student Progress & Lifecycle

A `student` is a **person** — identity, address, date of birth, guardians, permit details. Program state (required hours, progress, completion, license type) lives on that person's **enrollments**, not on the student row. This split exists because a driving school actually offers two distinct programs a person may take independently: see §11 "Enrollments" for the full model. This section covers the progress-calculation and completion mechanics that now operate on an enrollment.

Progress is derived live, never stored as a running total. `enrollments` has no hours-completed column at all — carrying one forward from the old `students.total_hours_completed` (a dead legacy column that nothing wrote to) would have recreated the exact stale-cache trap this design avoids.

- **Track derivation** (`backend/src/services/studentProgressService.ts`, `computeStudentProgress`): unchanged in algorithm, changed in input — it takes an enrollment's `hoursRequired`/`completed`/`completedAt`/`completionReason`/`trackOverride` plus the person's `dateOfBirth` (passed separately, since identity stays on the student). A student's age is computed live from `date_of_birth` (never persisted). Minors (under 18, or `date_of_birth` null) progress on an **hours track** against the enrollment's `hours_required`, defaulted at creation from the tenant's `tenant_settings.default_hours_required`. Adults (18+) progress on a **lessons track** — booked-lesson count vs. completed-lesson count, since adults have no mandated hour minimum. `enrollments.track_override` (`'hours' | 'lessons' | null`) lets an admin pin a track regardless of age (used at the turning-18 boundary), scoped to the specific enrollment.
- **Lesson-equivalent view** (`tenant_settings.standard_lesson_length_minutes`, integer, default 120): `computeStudentProgress` uses it to derive `lessonsRequired = ceil(hoursRequired * 60 / standardLessonLengthMinutes)` for minors, attached to the `StudentProgress` payload alongside the existing hours fields. Adults' `lessonsRequired` is simply an alias for their existing `lessonsBooked`. `percentComplete` is derived from the lesson-count view on both tracks.
- **Completion**: `enrollments.completed`/`completed_at`/`completed_by`/`completion_reason` are the sole source of truth for program completion on that enrollment — not an hours-threshold auto-derivation. `POST /api/v1/enrollments/:id/complete` sets these columns and computes `completion_hash` (see §12). The minor-needs-guardian gate (§8) still evaluates against the **person**, resolved from the enrollment's `student_id`.
- **Reopen is a guarded write**, not a plain undo: `POST /api/v1/enrollments/:id/reopen` requires a non-empty `reason` in the body and is restricted to `owner`/`admin` roles (`requireRole`). It records `reopened_at`/`reopened_by`/`reopened_reason` — a new event, not an erasure — and deliberately never clears `completion_hash`, since the historical fact "a completion occurred" must survive a later reopen. It returns `certificateExists: boolean` (a lookup against `certificates.student_id` — see the TODO in §11 on why this is person-scoped, not yet enrollment-scoped) so the caller can warn the user; the endpoint itself does not touch the certificate row.
- **Read-path attachment**: every student list/detail read (`getAllStudents`, `getStudentById`, `getStudentsByStatus`, `getStudentsByInstructor`) attaches a `progress` object derived from that student's **active** `driver_training` enrollment, via one batched query (not N+1). A student with no active `driver_training` enrollment (their prior one completed and no new one has started — a legitimate, common state, not an error) gets `progress: undefined`; `StudentProgressBar` renders "No active enrollment" for it, distinct from the zero-progress state.
- **Notifications**: the `notifications` table (fully defined in the baseline schema, previously unused) is now live. `backend/src/services/notificationService.ts` creates a `follow_up_due` notification when a lesson is marked `no_show`, auto-dismissed when that student's next lesson is booked. `backend/src/services/dashboardService.ts` — the first dedicated backend aggregation service — joins `lessons.status='no_show'` against active notifications to surface a no-show follow-up alert list.
- **New endpoints**: `POST /api/v1/enrollments/:id/complete`, `POST /api/v1/enrollments/:id/reopen`, `GET /api/v1/dashboard/no-show-alerts`, `POST /api/v1/dashboard/alerts/:notificationId/dismiss`.

## 7. Tenant Timezone Authority

Every date, "today"/"tomorrow" calculation, wall-clock interpretation, and derived age in this codebase resolves against the **tenant's** configured timezone (`tenant_settings.timezone`) — never the server's own timezone, and never the browser's. This must hold regardless of what physical machine or region the Node process happens to run in, since the product is sold to driving schools nationwide. `timezone` is nullable and, as of migration 011, has no DB-level default — a newly created tenant starts with it genuinely unset (see "Timezone auto-detect" below); `resolveTenantTimezone` is what turns that `null` into a concrete zone for actual date math.

### Wall-clock storage, tenant-relative interpretation

**Storage is unchanged and does not encode a timezone.** The 84 `timestamp without time zone` columns, plus every `date`/`time` column, remain exactly as they are — a 2pm lesson is stored as wall-clock `14:00:00` and stays `14:00:00` across a daylight-saving transition. This is the correct design for scheduling: a lesson booked for "2pm" means 2pm in the tenant's own clock, not a fixed instant that would silently drift an hour twice a year. What changed is **interpretation** — which timezone a stored wall-clock value or a computed "today" is understood to mean when it's read, compared, or converted to/from a real UTC instant.

### The helper module — the single entry point

All tenant-timezone date math lives in **one** module: `backend/src/utils/tenantTime.ts`. No other backend file reimplements offset/DST logic, and none of it is ported into the frontend. Built on `date-fns` + `date-fns-tz`, which read the IANA tzdata bundled with Node's own ICU build — the same source of truth browsers and operating systems use, rather than hand-rolled and inevitably incomplete offset arithmetic.

Primitives exported:
- `resolveTenantTimezone(timezone)` — the configured zone, or the documented default (`DEFAULT_TENANT_TIMEZONE = 'America/Los_Angeles'`) when `null`/`undefined`/empty. This is the only place an unset timezone becomes a concrete zone for real date math.
- `tenantToday(timezone, reference?)` / `tenantTomorrow(timezone, reference?)` — today's/tomorrow's date as `YYYY-MM-DD` in the tenant's zone.
- `addTenantDays(dateStr, days, timezone)` — walks a date string forward/backward within the tenant's zone (used for day-by-day iteration instead of mutating a `Date` with `setDate`).
- `formatInTenantZone(date, timezone, formatStr?)` — formats a real UTC instant (a `Date`) as a string in the tenant's zone. Never `toISOString().split('T')[0]` for this — that reads the UTC calendar date, which differs from the tenant's for roughly half of every day.
- `zonedWallClockToUtc(dateStr, timeStr, timezone)` — the inverse: given a tenant wall-clock date+time, returns the correct UTC instant. This is the primitive that fixes slot serialization and lesson storage; it replaces both `new Date(); date.setHours(...)` (which sets the *process's* local time) and naive `` `${date}T${time}` `` string parsing (ambiguous — parsed as either UTC or process-local depending on the exact string shape).
- `tenantMonthBoundaries(timezone, reference?)` — start/end of a month in the tenant's zone, correct even when the reference instant's UTC month differs from the tenant's.
- `tenantDayOfWeek(dateStr, timezone)` — day-of-week for a date string, resolved in the tenant's zone rather than the process's.
- `parseTenantDateOnly(dateStr)` — parses a `YYYY-MM-DD` string into a `Date` at UTC midnight of that calendar date, for callers (e.g. `calculateAge`) that need to compare year/month/day components, not a real instant.

One exception is explicitly safe and does **not** go through the helper: extracting the calendar date from a plain Postgres `DATE` column value (e.g. `lessons.date`). A `Date` instance `pg` returns for a `DATE`-typed column is always UTC midnight of that calendar date — there's no wall-clock time attached, so `toISOString().split('T')[0]` carries no roll risk there specifically. This is called out inline with a comment everywhere it's used, so it isn't "fixed" by a future reader who doesn't realize the distinction. Contrast this with the same pattern applied to a real timestamp/instant value (e.g. a lesson's resolved start time), which *is* a live bug this module exists to eliminate.

### Where this applies

- **Scheduling** (`schedulingService.ts`): slot generation, date-range interpretation, "today"/"tomorrow" search-window origin, and conflict-detection date/time-string derivation all resolve in the tenant's zone.
- **Lesson storage** (`lessonService.ts`): a lesson's stored `date`/`start_time`/`end_time` are derived from the tenant zone consistently (previously the most severe bug found — the date was read in UTC while the time was read in server-local time, an internal inconsistency that could store a lesson on the wrong calendar day).
- **Lesson invites and calendar feeds** (`lessonInviteService.ts`, `calendarFeedService.ts`): invite date text and `.ics` `DTSTART`/`DTEND` resolve in the tenant zone. Both emit `DTSTART`/`DTEND` as UTC instants (`Z`-suffixed, RFC-5545-legal) rather than hand-rolling a `VTIMEZONE` block with baked-in DST transition rules for one hardcoded zone — every mainstream calendar client renders a UTC-suffixed `DTSTART` correctly in the viewer's own local time, and this approach doesn't require re-deriving IANA's DST rules for 400+ zones.
- **Admin cancellation actually reaches the instructor's subscribed calendar** (`calendarFeedService.generateICSFeed`, `GET /calendar-feed/:token.ics` in `app.ts`): the feed's lessons query previously filtered `WHERE l.status IN ('scheduled', 'completed')` — a cancelled lesson never reached the `STATUS:CANCELLED`-emitting code below it at all, so cancelling a lesson silently dropped its row from the feed's SQL result instead of telling the subscriber to remove it. Some calendar clients leave a stale "ghost" event behind when a previously-seen UID just disappears from a feed rather than being explicitly cancelled, so the query now includes `'cancelled'` (and `'no_show'`) and lets the existing per-event `STATUS:CANCELLED`/`STATUS:CONFIRMED` branch do its job — the same stable UID (`lesson-{id}@budgetdrivingschool.com`) is kept either way, which is what lets a subscribed client match the existing event and remove it rather than never seeing anything change. `no_show` stays `STATUS:CONFIRMED` (visible, not cancelled) — the instructor was actually there and that time was spent/blocked regardless of whether the student showed. Since admin is the schedule's single source of truth (instructors don't cancel in-app), this is the only cancellation path that needed fixing.
  - **Refresh promptness**: a subscription feed is pull-only — the client decides when to re-poll, and with no hint Google in particular may only poll about once a day, so a cancellation could sit stale on an instructor's calendar until the next day. The `VCALENDAR` now emits `X-PUBLISHED-TTL:PT1H` and `REFRESH-INTERVAL;VALUE=DURATION:PT1H` (both say "re-check within an hour"; emitting both maximizes client support across the de facto Apple/iCal convention and the newer RFC 7986 property). `Content-Disposition` changed from `attachment` (forces a download prompt) to `inline` (lets Google/Apple's "add calendar from URL" treat it as a live subscription instead of a one-time file). `Cache-Control` changed from `no-cache, no-store, must-revalidate` (fights caching for no benefit — nothing here is sensitive enough to require disabling it) to `private, max-age=300`, complementing rather than fighting the feed's own hourly refresh hints. **Honest caveat**: these are hints, not guarantees — exact re-poll timing is entirely up to the subscribing client, so "prompt" here means observed within roughly an hour for clients that honor the hints (confirmed live: booking and cancellation both reach a re-fetched feed immediately server-side; the pull-based delay is purely how soon Google/Apple/Outlook's own poller comes back), not instant push.
  - **Live-verified end-to-end**: subscribed to a real instructor's feed token, booked a lesson (appeared as `STATUS:CONFIRMED` with a stable UID), admin-cancelled it via `POST /lessons/:id/cancel`, re-fetched the feed — same UID now `STATUS:CANCELLED`. Confirmed `DTSTART` was tenant-time-correct (13:00 `America/Los_Angeles` on a PDT date → `20260904T200000Z`). Confirmed response headers: `Content-Disposition: inline`, `Cache-Control: private, max-age=300`, both refresh-hint properties present in the body.
- **Student age** (`studentProgressService.ts`'s `calculateAge`): a student's age — which gates the adult-email requirement and the hours/lessons progress track — transitions on the tenant's calendar day, not the server's or UTC's.
- **Review queue** (`dashboardService.ts`'s `getLessonsNeedingReview`): "has this scheduled lesson's end time already passed" resolves in the tenant zone via `zonedWallClockToUtc`, then plain instant comparison against "now" — never a client-side date check.
- **Cancellation fee window** (`lessonService.ts`'s `cancelLesson`): "is this cancellation within N hours of the lesson's start" resolves the lesson's start as a real UTC instant the same way, then compares the millisecond delta against `tenant_settings.cancellation_fee_window_hours`.

### Server timezone is irrelevant by design

The server process runs with `TZ=UTC` (`.env.example`, `.env.test`, and the CI workflow's job-level `env`) — not because UTC is privileged, but to make "the server's own timezone must never matter" an enforced, testable fact rather than an incidental one that happens to hold only on whichever machine a developer's shell defaults to. A structural test (`backend/src/__tests__/noServerLocalDateDerivation.test.ts`) statically scans every file in the list above for `toISOString().split('T'`, `.getFullYear()`/`.getMonth()`/`.getDate()`/`.getDay()`, and bare `new Date()` outside a small, explicitly documented allowlist (DATE-column extraction, RFC 5545 `DTSTAMP`, instant-vs-"now" comparisons, and the helper module's own default-reference parameters). A companion hostile-clock test suite (`tenantTimeHostileClock.test.ts`) exercises the helper primitives, `calculateAge`, and slot generation against `America/New_York` (DST-observing) and `America/Phoenix` (no DST) tenants while the process itself runs UTC, including at instants where the UTC calendar date and the tenant's disagree.

### Timezone auto-detect (Settings UI convenience, not an exception to the rule above)

`frontend/src/pages/Settings.tsx`'s General tab is the one place the frontend is allowed to call `Intl.DateTimeFormat().resolvedOptions().timeZone` — and even there, the result is never used for date math, only to pre-populate a suggestion an admin must explicitly accept and then explicitly save. The suggestion banner renders only while `tenant_settings.timezone` is `null` (never configured — see migration 011, which dropped the column's DB-level default so a new tenant starts unset instead of silently landing on the old Pacific default). Accepting the suggestion sets the ordinary form field; nothing is persisted or treated as authoritative until the existing `PUT /tenant/settings` save path runs, going through the same `Intl.supportedValuesOf('timeZone')` validation as any manually-typed zone. Existing tenants already sitting at the pre-migration default value are not backfilled to `null` and so never see the suggestion — there's no way to tell whether that value was an explicit choice.

### Frontend consumption: `tenantNow`, never the browser's own clock

The frontend never computes a timezone boundary itself — every "today"/"this week"/"this month" surface renders a value the backend already resolved. `GET /api/v1/tenant/settings` returns a `tenantNow` object (`tenantService.getTenantNow`, a thin composition of the primitives above) alongside the existing settings payload:

```ts
interface TenantNow {
  timezone: string;
  today: string;       // YYYY-MM-DD
  tomorrow: string;     // YYYY-MM-DD
  currentTime: string;  // HH:MM, tenant wall-clock
  weekStart: string;    // YYYY-MM-DD, Sunday-start (see note below)
  weekEnd: string;      // YYYY-MM-DD, weekStart + 6
  monthBoundaries: { start: string; end: string };
}
```

`frontend/src/contexts/TenantContext.tsx` exposes this via `useTenant().tenantNow`, refetched every 5 minutes alongside the rest of `TenantSettings` (no separate API call). Sunday week-start is a documented convention inside `getTenantNow`, not a hardcoded law — it may become a tenant setting later, mirroring `cancellation_fee_window_hours` and similar.

Every previously browser-local surface now consumes `tenantNow` (or a value derived from it) instead of `new Date()`:
- **`Dashboard.tsx`**: renders a loading state until `tenantNow` resolves — deliberately no browser-`Date` fallback, since a brief wrong-day flash is worse than a brief spinner. Today's-lessons count, the 30-day permit-expiry boundary, monthly revenue, and the "Next 7 Days" grid all key off `tenantNow`.
- **`Lessons.tsx`**: status counts, stats, and `groupLessonsByDate`'s Today/Tomorrow/This Week/Later/Past buckets compare `lesson.date` (a plain `YYYY-MM-DD` string) directly against `tenantNow` fields — never `new Date(lesson.date).toISOString().split('T')[0]`, which UTC-shifts a date-only value.
- **`LessonsCalendarView.tsx`** / **`InstructorWeeklySchedule.tsx`**: month/week navigation and the "today" highlight seed from `tenantNow.today`/`tenantNow.weekStart` via `parseLocalDate`; subsequent calendar-grid math (`.getDay()`, `.getDate()`, `setDate`) operates on that already-tenant-anchored `Date`, which is safe — it's pure calendar arithmetic on a resolved value, not a fresh read of the browser's instant (the same distinction `parseLocalDate`/`formatLocalDate`/`addCalendarDays` in `timeFormat.ts` document for themselves).
- **`utils/studentStatus.ts`**: `computeStudentStatus`/`studentNeedsFollowup`/`getFollowupReason` all take a **required** `now: Date` parameter — no default — so a caller that forgets to pass tenant time is a compile error, not a silent browser-time fallback. Callers (`Dashboard.tsx`, `Students.tsx`) pass `parseLocalDate(tenantNow.today)`.
- **`SmartBookingForm`**: `findAvailableSlots`'s response gained `startTimeLocal`/`endTimeLocal` (tenant wall-clock `HH:MM`, sibling fields to the existing ISO `startTime`/`endTime`) on `TimeSlot`/`RankedTimeSlot`. The wizard's booking payload and every displayed slot time now read these directly, eliminating the old `new Date(iso).getHours()` parse that was correct only when the browser's zone happened to match the instant's encoding.
- **`DateRangeFilter.tsx`**: stays presentational — takes `tenantToday`/`tenantWeekStart`/`tenantWeekEnd`/`tenantMonthStart`/`tenantMonthEnd` as props rather than calling `useTenant()` or `date-fns`'s `new Date()`-based boundary helpers itself.

**Enforcement**: `frontend/src/__tests__/noBrowserLocalDateDerivation.test.ts` mirrors `noServerLocalDateDerivation.test.ts`'s static-scan mechanism against these same files, with an explicit per-file allowlist for the legitimate calendar-grid-math cases described above. Hostile-clock test suites (`*.hostileClock.test.tsx`/`.ts`, one per surface above) reassign `process.env.TZ` at runtime to simulate a disagreeing browser timezone (verified to genuinely affect every `Date.prototype` getter and `Intl.DateTimeFormat`, including across DST transitions) while a separately mocked `tenantNow` simulates the backend-resolved value, asserting each surface renders the *tenant's* boundaries in both directions (tenant Pacific/browser Eastern and the reverse). **`date-fns-tz` must never be added to the frontend** — plain `date-fns` remains fine only for calendar-day arithmetic on an already-resolved string, never for converting an instant.

## 8. Guardians

Guardians are tenant-scoped records, independent of students, linked via a many-to-many junction table — the first such junction table in this schema.

**Guardians link to the person, not the program.** `student_guardians.student_id` references `students.id` — the person — and this did not change when program state moved to `enrollments` (§11). A person with two enrollments (e.g. driver training now, driver education completed years ago) still has exactly one set of guardians. The minor-requires-guardian gate at program completion likewise evaluates against the person, resolved from the enrollment being completed.

- **`guardians`** (`backend/database/migrations/005_add_guardians_table.sql`): `id` (uuid), `tenant_id`, `first_name`, `last_name`, `email`, `phone`, audit columns (`created_by`/`updated_by`). A DB `CHECK` constraint requires at least one of `email`/`phone`. **Deliberately no unique constraint** on email or phone — two guardian records may legitimately share contact info (e.g. divorced parents), and enforcing uniqueness would force a merge decision at write time. Visible to all authenticated tenant roles; unlike students, there's no instructor-data-isolation branch, since a guardian isn't owned by one instructor.
- **`student_guardians`** (`backend/database/migrations/006_add_student_guardians.sql`): many-to-many link, `(student_id, guardian_id)` unique, `relationship` (`mother`/`father`/`grandparent`/`legal_guardian`/`other`), `is_primary`. A partial unique index on `(student_id) WHERE is_primary` enforces exactly one primary guardian per student; promoting a new primary demotes the old one inside a real transaction (`backend/src/services/studentGuardianService.ts`'s `setPrimaryGuardian`, built on the `getClient()` seam). Deleting a student cascades its links; deleting a guardian is blocked with a clear, student-naming error while links exist (`guardianService.deleteGuardian`'s proactive pre-check; the DB's `ON DELETE RESTRICT` is a backstop, not the primary UX).
- **Explicit linking only**: `linkGuardianToStudent(studentId, guardianId, ...)` is the function that writes a single new `student_guardians` row outside of student creation, and it requires both IDs from the caller. Guardian *matching* (`findGuardianCandidates`, `findExactGuardianMatch` in `guardianService.ts`) is read-only — it never links, only surfaces candidates with disambiguating context (linked student names) for a human to choose from. This split is deliberate: it's the seam a future public signup form will reuse without risking auto-merged/duplicate guardian records.
- **Changing an existing link**: `PUT /api/v1/students/:id/guardians/:guardianId` (`studentGuardianService.updateGuardianRelationship`) updates only the `relationship` column on an existing `student_guardians` row — relationship is a property of the link, not the guardian, so it's never edited on the guardian record itself. `PUT /api/v1/students/:id/guardians/:guardianId/primary` (`setPrimaryGuardian`) promotes a guardian to primary, demoting the previous primary in the same transaction. `DELETE /api/v1/students/:id/guardians/:guardianId` (`unlinkGuardianFromStudent`) removes a link; it first checks whether the student is a minor (age < 18 or null `date_of_birth`, same convention as `needsGuardian`) with exactly one linked guardian remaining, and rejects with a 400 rather than stripping a minor's last guardian. Every guardian-linked student's second-to-last guardian can still be unlinked freely — only the very last one on a minor is protected.
- **Atomic student+guardian(s) creation**: `POST /students/with-guardian` (`studentService.createStudentWithGuardian`) creates a student and creates-or-links **one or more** guardians inside one `BEGIN`/`COMMIT` transaction on the same `getClient()` connection. The request body is `{ student, guardians: [...] }` — an array of 1..N entries, each either `{ mode: 'existing', guardianId, relationship?, isPrimary? }` or `{ mode: 'new', firstName?, lastName?, email?, phone?, relationship?, isPrimary? }`. The response is `{ student, guardians: [{ guardian, link }, ...] }` (plural, one pair per array entry). All pre-transaction validation — contact-method/DOB/adult-email checks, duplicate guardian references within the request (same `guardianId`, or the same new-guardian email/phone), and a per-`mode: 'new'` exact-match check against existing guardians (409 on a match) — runs before `getClient()`/`BEGIN` is ever called, so an invalid request never opens a transaction. The contact-method check itself (`data.phone` or `data.emergencyContactPhone`) is age-gated: an adult must satisfy it from their own fields, but a minor may also satisfy it via any guardian in the request — a `mode: 'new'` entry's own `email`/`phone`, or a `mode: 'existing'` entry's guardian record (fetched via `getGuardianById` to check) — since a minor's real point of contact is often the guardian being linked alongside them, not a phone/email of their own. Inside the transaction, the student insert happens once, then every guardian in the array is inserted-or-looked-up and linked in a loop on the same client; a failure at **any** point — including partway through the guardian array — rolls back the student insert and every guardian/link processed so far, not just the first. Exactly one guardian ends up primary: the caller's explicit `isPrimary: true` if given (more than one is a 400), otherwise the first entry in the array. This is additive alongside the plain `POST /students` (unchanged, still used for adults and for minors whose guardian setup is deferred) and is the only path the frontend uses whenever a guardian is being linked at creation time — never a `create` call followed by separate link requests.
- **Guardian requirement for minors**: a minor student may still be created with zero guardians (a link needs a `student_id` that doesn't exist until after insert). A computed `needsGuardian` flag (true only for minors with no linked guardian) is attached to every student read, batched alongside `progress`. The only hard gate is at program completion — `markStudentCompleted` rejects while a minor still `needsGuardian`. The frontend surfaces this proactively (a warning banner on existing flagged records, a "Needs Guardian" badge/filter on the Students list) so admins can correct records predating the guardian UI — including students created before the multi-guardian sub-panel shipped, since the guardian picker is no longer gated to create-mode-only (see Frontend below).
- **`students.email` is now nullable**, protected by a partial unique index (`idx_students_email_tenant ... WHERE email IS NOT NULL`) instead of a plain unique index — this unblocks enrolling minor siblings who share a parent contact or have no email of their own. Required server-side for adults (18+ by `date_of_birth`), enforced at both create and update; can't be a DB constraint since age changes daily.
- **Cross-entity search**: `GET /api/v1/search/people?q=` (`backend/src/services/searchService.ts`) searches students and guardians together by name/email/phone in one `UNION ALL` query, returning typed (`'student' | 'guardian'`) results. The frontend wires this into the Students page's shared search bar — typing 2+ characters overlays mixed results regardless of which tab (Students/Guardians) is active.
- **Emergency contact cleanup**: the legacy `students.emergency_contact` combined string column is dropped; `emergency_contact_name`/`emergency_contact_2_name` are split into `_first_name`/`_last_name` pairs for consistency with how names are stored elsewhere (`students.first_name`/`last_name`, `guardians.first_name`/`last_name`). These fields are collapsed behind progressive disclosure in the UI (see BLUEPRINTS.md) but remain structurally unchanged in the schema and API.
- **Frontend**: `frontend/src/pages/Students.tsx` has a Students | Guardians segmented tab sharing one page shell (no new nav item). `frontend/src/components/guardians/` holds `GuardiansList`, `GuardianModal` (detail + "Enroll another student"), `DuplicateGuardianConfirm`, and `UnifiedSearchResults`. `frontend/src/components/students/GuardianSubPanel.tsx` is a reusable, presentation-only linked-guardians list (row per guardian: name, relationship select, contact, primary star, unlink) used by `StudentModal.tsx` in both modes: in edit mode its callbacks call the guardian API immediately (`linkToStudent`/`unlinkFromStudent`/`updateRelationship`/`setPrimary`); in create mode they mutate a local `stagedGuardians` array, with nothing sent to the server until the whole form (student + all staged guardians) is submitted in one `createWithGuardian` call. The type-ahead picker (`guardiansApi.findCandidates`) and its "Create new guardian instead" option are shared by both modes — selecting or creating a guardian never links/stages immediately by itself, only on the sub-panel's explicit "Add Guardian" confirmation (Constraint: matching surfaces candidates, it never auto-links).

## 9. Lesson Review, Cancellation Policy, and Fee Flags

- **`lessons.reviewed_by`/`reviewed_at`** (`backend/database/migrations/013_add_lesson_review_audit.sql`): nullable `uuid`/`timestamp`, `reviewed_by` FK to `users(id) ON DELETE SET NULL`, no index — the same audit-column shape as migrations 002/003. Set by `completeLesson`/`noShowLesson`/`cancelLesson` (`lessonService.ts`), each guarded by `assertLessonReviewable`, which rejects (409) transitioning a lesson that's already `completed`/`cancelled`/`no_show`.
- **Tenant settings** (`backend/database/migrations/014_add_lesson_review_settings.sql`, four discrete columns on `tenant_settings`, no settings jsonb):
  - `lesson_completion_mode` (`text`, default `'manual'`) — `'manual' | 'auto'` at the TypeScript layer; only `'manual'` has a job behind it (the review queue). `'auto'` is stored but inert.
  - `cancellation_fee_amount` (`numeric(10,2)`, default `50`).
  - `cancellation_fee_window_hours` (`integer`, default `24`).
  - `cancellation_fee_payee` (`text`, default `'instructor'`) — `'instructor' | 'school'`. No CHECK constraint on either enum-shaped column, matching the existing precedent (e.g. `country`) that tenant-settings enums are TS-union-typed only; `tenantService.updateTenantSettings` validates both against their allowed value sets.
- **`fee_flags`** (`backend/database/migrations/015_add_fee_flags.sql`; `enrollment_id` added by `018_add_enrollments.sql`): `id`, `tenant_id`, `student_id`, `enrollment_id`, `lesson_id`, `amount`, `reason`, `status` (`outstanding | cleared | waived | paid`, CHECK-constrained), plus nullable resolution-detail columns (`waived_by`/`waived_reason`/`waived_at`, `paid_payment_id`/`paid_at`). FKs to `tenants`/`students`/`enrollments`/`lessons` (`ON DELETE CASCADE`), `users` (`waived_by`, `ON DELETE SET NULL`), `payments` (`paid_payment_id`, `ON DELETE SET NULL`). Indexes on `student_id`, `tenant_id`, plus a partial index on `student_id WHERE status = 'outstanding'` (the hot-path "does this student owe anything" lookup). **`student_id` and `enrollment_id` are deliberately both present and mean different things**, unlike the plain duplication that `lessons.student_id`/`payments.student_id` represent (an enrollment already identifies its student on those two tables): `enrollment_id` is *provenance* — which program's lesson generated this fee, relevant to CVC §11108's cost-of-instruction record — while `student_id` is *who owes it*. A fee can clear against a **later** enrollment than the one that generated it (the student's next lesson, however it's booked, resolves the flag), so every student-facing query in `feeFlagService.ts` (`getOutstandingFlagsForStudent`, `clearOutstandingFlagsForStudent`, `recordPaymentForFeeFlag`) is intentionally person-scoped, not enrollment-scoped — this is not dead-column cleanup waiting to happen.
- **Structural isolation from revenue (Constraint A).** `fee_flags` is never joined into, or referenced by, `instructorService.getInstructorEarnings` (sums `lessons.cost` scoped to `status='completed'`) or any query touching `students.total_paid`/`outstanding_balance`. This isn't an application-level exclusion rule — nothing in `feeFlagService.ts` writes to those columns or tables at all, verified by both a runtime test suite (`backend/src/__tests__/feeFlags.test.ts`) and a static source-grep test asserting `instructorService.ts`'s source never contains the string `fee_flags`.
- **Write paths, all internal to `feeFlagService.ts`** (modeled on `studentGuardianService.ts`'s tenant-scoped-everywhere shape): `createFeeFlag` is called only from `lessonService`'s status-transition side effects (no-show; a cancellation inside the fee window), never a public endpoint of its own. `waiveFeeFlag(id, tenantId, userId, reason)` mirrors `markStudentCompleted`'s waive-with-attribution shape exactly. `recordPaymentForFeeFlag` re-checks `cancellation_fee_payee === 'school'` server-side (403 otherwise) before calling the existing `paymentService.createPayment` — the school-payee path is the only place a `fee_flags` row and a real `payments` row are ever connected, via `paid_payment_id`. `clearOutstandingFlagsForStudent` runs from `completeLesson` as a non-blocking side effect, clearing every outstanding flag for that student at once.
- **New endpoints**: `POST /lessons/:id/cancel` (replaces `DELETE /lessons/:id`), `GET /dashboard/review-queue`, `POST /dashboard/review-queue/:date/complete-all`, `GET /students/:studentId/fee-flags`, `GET /instructors/:instructorId/fee-flags`, `POST /fee-flags/:id/waive`, `POST /fee-flags/:id/record-payment`.

## 10. Instructor Licensing, Service Areas, and Expiry Notifications

- **`instructors.instructor_license_number` / `instructor_license_expiration`** (plain nullable columns, present since `001_baseline.sql`): the instructor's **Driving School Instructor License** (California DMV) — the credential to *teach*, distinct from the Driving School Operator License that licenses whoever manages the school. Renews every 3 years, via exam or an 18-hour DMV-approved continuing-education program. `createInstructor`/`updateInstructor` (`backend/src/services/instructorService.ts`) now read and persist both fields — previously the form collected a license number and the service silently discarded it (same bug class as the earlier `employmentType` fix). `instructors.drivers_license_number`/`drivers_license_expiration` also exist on the row but are intentionally left unwired in the UI — see BLUEPRINTS.md for why.
- **`instructors.is_de_teacher` / `de_credential_number` / `de_credential_expiration`** (Phase 3 of `docs/compliance-records-build-plan.md`, `025_add_driver_education_module.sql`): a classroom driver-education teaching credential — a genuinely different credential from the Driving School Instructor License above, so kept on separate columns rather than overloaded onto it (an instructor who teaches both classroom DE and behind-the-wheel holds two distinct credentials at once). No expiry-notification pipeline for this credential — `instructor_license_notifications` below is scoped to the BTW instructor license only; building an equivalent second pipeline was deferred pending confirmation that DE credentials actually expire on a trackable schedule.
- **`instructor_service_areas`** (`backend/database/migrations/016_add_instructor_service_areas.sql`): `id`, `tenant_id`, `instructor_id`, `zip_code` (`varchar(5)`, CHECK-constrained to exactly 5 digits), `created_at`. `UNIQUE (instructor_id, zip_code)`; FKs to `instructors`/`tenants` (`ON DELETE CASCADE`); indexes on `instructor_id`, `tenant_id`, and `zip_code` (the last for the batched membership lookup `findRankedAvailableSlots` performs — see §"Where this applies" below). **No rows for an instructor means "serves everywhere"** — an empty result from `instructorServiceAreaService.getServiceAreas` is the normal unconfigured state, not an error, enforced entirely in application code rather than a sentinel row. Managed via `GET`/`PUT /instructors/:id/service-areas` (`instructorServiceAreaService.ts`'s `setServiceAreas` bulk-replaces the whole list transactionally, validating every entry's 5-digit format and rejecting duplicates before opening the transaction — no partial save).
- **`instructor_license_notifications`** (`backend/database/migrations/017_add_instructor_license_notifications.sql`): dedup tracking for escalating license-expiry reminders. `id`, `tenant_id`, `instructor_id`, `expiration_date` (`date`), `threshold` (signed `integer` — days relative to expiry: `180`/`90`/`30`/`14`/`7` pre-expiry, `0` on the expiry date, a negative multiple of 7 post-expiry), `notified_at`. `UNIQUE (instructor_id, expiration_date, threshold)` is the actual dedup enforcement — `instructorLicenseNotificationService.ts`'s daily cron always attempts `INSERT ... ON CONFLICT DO NOTHING`, and only creates admin-facing notifications when that insert genuinely records a new row, so even a concurrent or retried run can't double-fire. Including `expiration_date` in the key is what makes editing an instructor's expiration reset the schedule for free: a new date has no matching rows yet, so every threshold fires fresh against it. Rows for a superseded date are left in place (audit trail), never queried again. FKs to `instructors`/`tenants` (`ON DELETE CASCADE`); index on `(instructor_id, expiration_date)`. The same migration widens `notifications.type`'s CHECK constraint to add `'license_expiring'` — the type these reminders create, one row per active owner/admin user in the tenant, via the same `notifications` table the no-show alert already uses (not the separate, unused `notification_queue` email pipeline — see BLUEPRINTS.md for why).
- **`backend/src/jobs/instructorLicenseCron.ts`**: a `node-cron` job, daily (`INSTRUCTOR_LICENSE_CRON_SCHEDULE`, default `0 8 * * *` server time), started from `backend/src/index.ts` at server startup. The schedule string is inherently server-local (cron scheduling always is), but the work inside resolves "today" per-tenant via `tenantToday(timezone)` before ever comparing dates — which server instant the job happens to fire at never affects which tenant-calendar-day a threshold is evaluated against.
- **`GET /api/v1/dashboard/license-expiry-alerts`**: live-computed on every call from `instructors.instructor_license_expiration` + tenant "today" (same pattern as the review queue, not the no-show alert's join-against-persisted-notification-state pattern) — instructors already expired or expiring within 180 days, sorted soonest-first. No dismiss endpoint; the alert clears itself the moment an expiration is edited past the window.

## 11. Enrollments

`students` carried `hours_required`, progress, and completion state directly for most of this project's history, which implicitly assumed one program per person. That's false: a driving school sells two distinct programs — **driver education** (30 hours, classroom/online) and **driver training** (6 hours, behind-the-wheel) — and a person may take either, both, or one here and one elsewhere, sometimes years apart. Certificates are issued per program on different DMV form types, and as of migration `021` they attach to the **enrollment**, not the person — see §13.

- **`enrollments`** (`backend/database/migrations/018_add_enrollments.sql`, `status` widened by `021_certificates_and_withdrawal.sql`): `id` (opaque `uuid`), `tenant_id`, `student_id`, `program_type` (`'driver_education' | 'driver_training'`, CHECK-constrained), `status` (`'active' | 'completed' | 'inactive' | 'suspended' | 'withdrawn'`), `enrollment_date`, `hours_required`, `track_override`, `assigned_instructor_id`, `license_type` (`'car' | 'motorcycle' | 'commercial'` — moved here from `students`, since it describes the program, not the person), `total_cost` (nullable — see below), completion columns (`completed`/`completed_at`/`completed_by`/`completion_reason`), reopen-audit columns (`reopened_at`/`reopened_by`/`reopened_reason`), withdrawal-audit columns (`withdrawn_at`/`withdrawn_by`/`withdrawn_reason` — see §13), the external-DE-prerequisite columns (below), and the BSV forward-compat columns (§12). FKs to `tenants`/`students` (`ON DELETE CASCADE`), `instructors`/`users` (`ON DELETE SET NULL`).
- **`withdrawn` is a distinct lifecycle outcome from `inactive`/`suspended`** — those two don't mean "the student left the program," `withdrawn` specifically does. `POST /api/v1/enrollments/:id/withdraw` (`enrollmentService.withdrawEnrollment`) is a guarded write mirroring `reopenEnrollment`'s exact shape: requires a non-empty `reason`, restricted to `owner`/`admin` via `requireRole`, only callable on an `active` enrollment (`409` otherwise — completion and withdrawal are mutually exclusive outcomes for one enrollment). Exists specifically to support the §13.6 training-received transcript, which states the withdrawal date and reason.
- **At most one *active* `driver_training` enrollment per student** — a partial unique index on `(student_id) WHERE program_type = 'driver_training' AND status = 'active'`, not "one ever." A completed, inactive, or suspended enrollment does not block a new active one for the same program type — this is what lets a returning student (e.g. car training in 2026, motorcycle training in 2028) get a second `driver_training` enrollment. Every "resolve the student's driver_training enrollment" call site (lesson/payment/fee-flag creation, progress attachment, completion) resolves the active one specifically; a student with none gets a clean `400` on write, or `progress: undefined` on read (§6), never a silent failure.
- **Scope this session**: `driver_training` is built fully — hours, progress, completion, lessons, fee flags, review queue. `driver_education` exists as a program type and can be created with manually entered completion date and hours (`enrollments.manual_completed_hours`) — no lesson tracking, no scheduling, no curriculum for it yet.
- **External driver education prerequisite**: `driver_training` enrollments carry `external_de_completed`/`external_de_completed_date`/`external_de_provider`, recording whether DE was completed elsewhere (a different school, before this system was in use). Display-only — surfaced on the student record, not enforced or blocked on at booking time.
- **Derived payment totals, not stored**: `total_paid`/`outstanding_balance`/`payment_status` do not exist as columns on `enrollments` (or, as of migration `019`, on `students` either — the old `students.total_paid`/`outstanding_balance`/`payment_status` were confirmed stale, uncached columns, only ever written by a generic PATCH path and never kept in sync with `payments`). They're computed at read time (`enrollmentService.computePaymentSummary`) from `SUM(payments.amount) WHERE enrollment_id = ... AND status = 'confirmed'`, compared against `total_cost` — itself derived from the enrollment's own `lessons.cost` when not explicitly overridden (`tenant_settings.default_lesson_cost` is confirmed to be only a booking-wizard prefill, not an enforced formula, so it cannot substitute for summing actual lesson costs). `outstandingBalance` is `null` — not `0` — when neither an override nor any lessons exist yet, since "not computable" and "zero" are different facts. This mirrors `computeStudentProgress`'s derive-don't-cache precedent exactly.
- **`lessons.student_id` and `payments.student_id` were pure duplication** of `enrollments.student_id` and are now **dropped** (`backend/database/migrations/020_drop_lesson_payment_student_id.sql`), closing the deferral migration `019` left open. Every read site that used to select or filter on the column directly now resolves it via a join/subquery to `enrollments` (`e.student_id AS student_id` on `SELECT`s; a scalar subquery — `RETURNING` cannot join directly — on `UPDATE ... RETURNING`), so `Lesson.studentId`/`Payment.studentId` are unchanged in the returned shape at every call site, backend and frontend alike. `schedulingService.ts`'s ranked-slot search — the one query in this cleanup that runs on every single search, not just once per booking action — was verified via `EXPLAIN ANALYZE` against a synthetic 5,000-student/50,000-lesson dataset before the rewrite shipped: the join/subquery form plans as an index-scan-to-index-scan nested loop (`idx_enrollments_student` → `idx_lessons_enrollment`), no sequential scan, execution time statistically indistinguishable from the old direct-column filter. `fee_flags.student_id` is a different case and was never part of this cleanup — see §9.
  - **A real bug was found and fixed while auditing these read sites**: `updateLesson` let a lesson's student be reassigned via the live edit form but only wrote `student_id`, never `enrollment_id` — so `enrollment_id` silently kept pointing at the *original* student's enrollment after a reassignment, a genuine two-sources-of-truth data-integrity risk, not just column duplication. Fixed to resolve and write both columns together in the same `UPDATE` (rejecting with `400` if the new student has no active `driver_training` enrollment), mirroring how `createLesson` already resolves it. Migration `020` repairs any lessons that drifted under the old behavior before dropping the column that made the drift detectable. Worth remembering if a future column-duplication cleanup elsewhere in the schema turns up a similar write-one-of-two-FKs pattern: it is not automatically safe to drop the "duplicate" column without first confirming every write path that can change one also changes the other.
  - `paymentService.ts`'s `keysToCamel` gap noted here in an earlier revision of this section has since been fixed — see the git history for that commit; every `Payment` return site now applies `keysToCamel` like every other service.
- **New endpoints**: `GET/POST /api/v1/students/:id/enrollments` (list/create, nested — matches the `/students/:id/guardians` pattern), `GET/PATCH /api/v1/enrollments/:id`, `POST /api/v1/enrollments/:id/complete`, `POST /api/v1/enrollments/:id/reopen`, `POST /api/v1/enrollments/:id/withdraw`, `GET /api/v1/enrollments/:id/withdrawal-transcript` (flat — an enrollment id is already tenant-unique, and this matches how lesson actions are routed, e.g. `POST /lessons/:id/cancel`).
- **Frontend**: the student modal gained an Enrollments tab (`EnrollmentSubPanel.tsx`, following `GuardianSubPanel.tsx`'s dumb-component-plus-parent-owns-mutations contract) alongside the existing Details/Progress/History tabs — edit-mode-only, since a new student already gets exactly one `driver_training` enrollment automatically at creation (no create-mode staging needed, unlike guardians). "Add enrollment" is gated independently per program type and is always an explicit two-step action. The same tab now also carries Withdraw (active enrollments), Record certificate and the gold certificate badge, and Generate transcript (§13) — all the same explicit two-step-action contract. The Students list page is unchanged — it reads `student.progress`/`student.activeEnrollment`/`student.paymentSummary`, all still attached in list responses in the same shape as before.
- **"Mark complete" is not `driver_training`-only** — it was originally gated to `isDriverTraining && status === 'active'`, which left `driver_education` with no UI completion path at all (online DE could never reach a certificate worklist). Widened to `enrollment.status === 'active' && !enrollment.completed &&` one of: `driver_training` (unchanged); online DE (manual, no attendance gate — completion is inherently manual for online); or classroom DE gated on `classroomAttendance?.isComplete` (4/4 curriculum days, the same signal §13's combined "Complete & issue" action requires) — an admin cannot mark a 2/4 classroom student complete through this button and bypass the attendance requirement. Classroom DE therefore has two completion paths by design: this plain button (completed the days, certificate issued later) and §13's combined action (complete-and-issue in one step) — both call the same completion logic underneath.

## 12. BSV Forward-Compatibility (Enrollment Completion)

No blockchain code was written for this — this section documents groundwork only. An enrollment's **completion** is a point-in-time attestation, the fact a future certificate would rest on, and is the natural anchor unit per docs/MISSION.md's decision framework (it's a discrete, infrequent, high-value event — not a chokepoint, not a micro-fee action).

- `enrollments.completion_hash` (nullable `text`) is computed and stored by ordinary application code the moment `markEnrollmentCompleted` runs, using Node's built-in `crypto` module (`sha256`) over a small canonical JSON object: `{enrollmentId, programType, hoursCompleted, completedAt}` — internal IDs and non-PII scalars only, never a student's name, email, phone, or address. Reopening an enrollment never clears `completion_hash` — it's a historical record that a completion occurred, not something a reopen erases.
- `enrollments.ledger_txid` (nullable `character varying(255)`, matching the existing `bsv_transaction_id` nullable-column convention elsewhere) is written **nowhere** in this codebase and stays permanently `NULL`. A future session will populate it once real anchoring is wired.
- **No blockchain import anywhere in this path**: `enrollmentService.ts` never imports `walletService`, `treasuryService`, or the `Ledger` seam (`backend/src/services/Ledger/`) — enforced by a structural test (`backend/src/__tests__/enrollmentBsvForwardCompat.test.ts`), the same static-source-scan technique `feeFlags.test.ts` uses for revenue isolation.
- **The `LedgerService` interface needs zero changes** to support a future anchor call: `LedgerActionType` already reserves `'BDP_PROGRESS'` ("student progress update", 2 sats) with zero current callers — the natural landing spot. The two real production `anchorAction`/`recordPayment` call sites today (`lessonService.ts`'s booking side effect, `paymentService.ts`'s payment side effect) already demonstrate the "internal IDs only, never PII" calling convention this would follow.
- Enrollment IDs are opaque `uuid`s (`gen_random_uuid()`), and no student PII is denormalized onto the `enrollments` row anywhere — a future anchor payload can reference an enrollment by ID alone.

## 13. Certificate Issuance Tracking

California driving schools issue DMV certificates of completion (DL 400D for behind-the-wheel driver_training; DL 400B/DL 400C for classroom/online driver_education — see the form-type note below) to minors who complete their program. 13 CCR §340.27 requires each certificate recorded in numerical sequence with student name and issue date, a void/lost/stolen accounting (the DL 803 log), and a transcript of training received on request for a minor who withdraws before completing.

**The real workflow, not an idealized one**: instructors hold physical certificates and hand one to a student at their final lesson, writing the serial on the student's paper record sheet. Sheets come back to the admin, who enters the serial against the enrollment afterward. The app is a **reconciliation system of record**, not a live-issuance system — nothing creates a certificate automatically at enrollment completion.

- **The `certificates` table already existed** (`001_baseline.sql`) but was never wired to a real feature — zero rows in every environment, exactly one narrow reader (`enrollmentService.reopenEnrollment`'s `certificateExists` check), and shaped for a person-scoped, ad-hoc-blockchain-column model that didn't fit this feature. Reshaped in place by `021_certificates_and_withdrawal.sql` (altered, not dropped-and-recreated, since zero rows meant no backfill risk) into an **enrollment-scoped** compliance record: `id`, `tenant_id`, `enrollment_id` (nullable — a void has no enrollment, FK to `enrollments.id`, no `ON DELETE CASCADE` — a certificate is a compliance record, so deleting an enrollment must not silently delete proof a certificate was issued), `serial_number`, `form_type` (free-text, no CHECK constraint — see the form-type note below), `status` (`'issued' | 'void'`, plain CHECK — `'assigned'/'pending'` are reserved for a future physical-custody feature, not built this session), `void_reason`, `issue_date`, `completion_hash`/`ledger_txid` (BSV forward-compat, see below), `created_at`/`updated_at`. Unique index on `(tenant_id, serial_number)`; indexes on `enrollment_id` and `(tenant_id, status)`.
- **Form type is resolved explicitly, never defaulted** (`024_fix_certificate_form_type.sql`, Phase 2; extended to `driver_education` by `025_add_driver_education_module.sql`, Phase 3, of `docs/compliance-records-build-plan.md`): `021`'s original `form_type` column defaulted to `'DL_400C'`, so every certificate silently inherited that default regardless of program — wrong for every `driver_training` certificate (the only kind this app recorded at the time), which belongs on DL 400D. `certificateService.recordCertificate` derives `form_type` from the enrollment: `driver_training → 'DL_400D'`; `driver_education` resolves by its `de_delivery_mode` column (Phase 3) — `'classroom' → 'DL_400B'`, `'online' → 'DL_400C'` — and throws a 400 if a `driver_education` enrollment has no delivery mode set (only possible for a row created before Phase 3 existed). `recordVoid` sets an explicit `'NOT_APPLICABLE'` sentinel — a void was never associated with a program, so it has no real form type to derive. The column's `DEFAULT 'DL_400C'` was dropped entirely (not replaced with a different hardcoded default) so `form_type` is always set explicitly by the app; a future insert path that forgets it now fails loudly (`NOT NULL` violation) instead of silently mislabeling a certificate again.
- **Two different people, two different columns — do not collapse them**: `issued_by_instructor_id` (nullable, FK to `instructors.id`) is the instructor who physically handed the certificate to the student — the DMV-relevant party. `recorded_by` (FK to `users.id ON DELETE SET NULL`, matching `enrollments.completed_by`/`fee_flags.waived_by`'s convention) is the admin who later entered the serial in the app from the returned paper sheet — the data-entry audit trail. Often a different person, sometimes a different day. A void certificate has `issued_by_instructor_id = NULL` (never issued to anyone) but always has `recorded_by` set.
- **Sourcing the issuing instructor's default**: when recording a certificate from a completed enrollment, `certificateService.recordCertificate` pre-fills (editable, never authoritative) `issued_by_instructor_id` from that specific enrollment's own most recent **completed** lesson's instructor — enrollment-scoped, not person-scoped, since a person can have multiple enrollments with different instructors — falling back (Phase 3) to the enrollment's home `de_cohorts.teacher_instructor_id` if it has one (classroom `driver_education` has no lessons but does have a cohort), then to `enrollments.assigned_instructor_id` if neither resolves. The admin can always override from the sheet; the field is left empty rather than guessing if no default resolves.
- **Recording is gated by whether a certificate was issued, never by age.** `recordCertificate` has no age check whatsoever and is callable on any completed enrollment — an adult's certificate, or any completed enrollment outside the awaiting-certificate worklist. Age only decides what the worklist *surfaces*, never what recording *permits*.
- **The awaiting-certificate worklist** (`GET /certificates/worklist`, `certificateService.getAwaitingCertificateWorklist`): completed `driver_training` enrollments with no certificate row yet, **plus** (Phase 3) completed `driver_education` enrollments that have a `de_delivery_mode` set (classroom or online alike — both need a certificate; the form type is resolved separately, see above), filtered to students who were **minors as of the enrollment's own `completed_at`** — not today's date. A student who has since turned 18 still surfaces if they were a minor when they completed; this same minors-only rule applies uniformly to both program types per the documented §340.27 requirement, with no adult carve-out for `driver_education`. ## 14. Driver Education Tracking Module (Phase 3, in progress)

An administrative tracking tool for driver education the school teaches itself — not a course-delivery platform (no content/quizzes/exams). Off by default per tenant. Builds out the **classroom** delivery (DL 400B) properly; **online** (DL 400C) stays exactly as minimal as `driver_education` already was — `manual_completed_hours`, untouched by this phase.

- **Schema** (`025_add_driver_education_module.sql`): `de_cohorts` (a class: 4 sessions + a teacher + a capacity; `status` is a light, cosmetic bookkeeping field only — `'scheduled' | 'completed' | 'cancelled'` — never load-bearing for completion logic), `de_cohort_sessions` (the 4 specific class dates, each tagged `curriculum_day` 1-4 via `UNIQUE (cohort_id, curriculum_day)` — the four days cover distinct material and are not interchangeable), `de_cohort_enrollments` (a student's ONE home cohort — `UNIQUE (enrollment_id)` — for the roster view and make-up bookkeeping), `de_attendance` (the completion source of truth — see below). Also: `enrollments.de_delivery_mode` (`'classroom' | 'online' | null`, feeds the form-type mapper, §13), `instructors.is_de_teacher`/`de_credential_number`/`de_credential_expiration` (a classroom teaching credential, deliberately **separate** from `instructorLicenseNumber`/`instructorLicenseExpiration` — the Driving School Instructor License is a different credential tied to its own expiry-notification system, §10; no expiry-notification pipeline built for the DE credential this phase — recorded field only), `tenant_settings.enable_driver_education`/`de_discount_amount` (feature flag + editable BTW discount amount), `lessons.de_discount_applied` (auditability for the discount, see below once built).
- **Completion is never a per-cohort flag** — this is the core design constraint. `de_attendance` rows are a fact about `(enrollment_id, session_id)`: which specific session (any cohort's) a student attended. A student's completion is `COUNT(DISTINCT curriculum_day) = 4` across every `present = true` row for their `enrollment_id`, regardless of which cohort each session belongs to. This is what makes a cross-cohort make-up (attend Day 2 at a cohort other than your home one) correctly count: the student's home cohort (`de_cohort_enrollments`) only decides which roster they show up on by default and where make-up guests are visually distinguished from home students — it never gates or computes completion. The "a student can only be present at one curriculum_day once, ever, across all cohorts" rule spans sessions via `curriculum_day` and so is a service-layer invariant (checked before every attendance insert), not a single-table SQL constraint; `de_attendance`'s own `UNIQUE (enrollment_id, session_id)` only prevents a duplicate write for the exact same session.
- **Cohort cancellation** doesn't touch `de_attendance` (days already attended stay attended) or `de_cohort_enrollments` (home-cohort membership is kept as history). It surfaces an actionable list of that cohort's students who still have unattended curriculum days, generated from the same attendance-gap computation the ordinary make-up flow needs — re-slotting those students uses the identical cross-cohort day-assignment flow as any other make-up, not a separate mechanism.
- **`enableDriverEducation`** (`tenant_settings`, off by default): the first non-baseline boolean feature flag in this codebase. Gates the `Classroom` nav item (`Sidebar.tsx`, same `featureFlag` pattern as `enableCertificates`) and, unlike every existing flag, the **route itself** — `App.tsx`'s `FeatureFlagRoute` wrapper redirects `/classroom` to the dashboard when the flag is off, rather than only hiding the nav link and leaving the page reachable-but-broken by direct URL (the gap the existing `enableCertificates`/`/certificates` pairing has). Edited via a normal checkbox in `Settings.tsx`'s `GeneralSettings` form (typed against `TenantSettings`, saved through the existing PUT), not a special-cased raw-`fetch` toggle like the pre-existing "Power Mode" button.
- **Instructor DE-teacher form** (`InstructorModal.tsx`): a checkbox ("Qualified to teach driver education classes") that conditionally reveals the credential number/expiration fields, in their own section distinct from the Driving School Instructor License section above it. `instructorService.ts`'s `createInstructor`/`updateInstructor` persist all three fields the same way they already persist `instructorLicenseNumber`/`instructorLicenseExpiration`.
- **Cohort/session CRUD** (`backend/src/services/classroomService.ts`, `POST`/`GET`/`PATCH /api/v1/classroom/cohorts[/:id]`, `GET /api/v1/classroom/cohorts/:id/gaps`): `createCohort` validates its 4 sessions cover curriculum days 1-4 exactly once each (400 otherwise — the same structural invariant `de_cohort_sessions`'s own `UNIQUE (cohort_id, curriculum_day)` enforces at the DB layer, checked earlier so a malformed request never reaches it) and, if a teacher is given, that the instructor is actually `is_de_teacher = true` (an instructor not so flagged can't be assigned, at creation or via `updateCohort`). `getCohorts`/`getCohortById` return each cohort with its 4 sessions (sorted by curriculum day) and a live `enrolledCount` (a `COUNT` subquery against `de_cohort_enrollments`, not a stored counter). `getCohortAttendanceGaps` is the query behind cancellation re-slotting (above): for one cohort's enrolled students, which curriculum days each is still missing across ALL their attendance (not just this cohort's sessions) — students with zero gaps are excluded, so the result is directly the actionable make-up list.
- **Attendance and completion** (`backend/src/services/classroomAttendanceService.ts`): `recordAttendance(sessionId, ...)` is the single write path for a checkbox on any session's roster — callable for a session belonging to the student's home cohort OR a different one entirely (a make-up), since it only needs a session id and an enrollment id, never a cohort-membership check. Before writing `present = true` it checks for an existing `present = true` row at the **same `curriculum_day`** on *any other session* for that enrollment (409 if found) — this is the cross-cohort double-booking guard, and it's necessarily a service-layer check (spans sessions via `curriculum_day`) rather than the DB-level `UNIQUE (enrollment_id, session_id)` constraint, which only stops a duplicate write for the exact same session. The write itself is an upsert (`INSERT ... ON CONFLICT (enrollment_id, session_id) DO UPDATE`), so toggling a checkbox off-then-on again doesn't error. `getClassroomAttendanceSummary`/`getClassroomAttendanceSummaries` (batched) compute `attendedCurriculumDays` and `isComplete` (`= 4` distinct days) by joining `de_attendance → de_cohort_sessions` on `enrollment_id` alone — no cohort filter anywhere in this query, which is what makes a Day-3 make-up at a different cohort count identically to attending Day 3 at the student's own cohort. `getSessionRoster` unions two sets for one session: the cohort's own enrolled students (`de_cohort_enrollments`, `isHomeCohort: true`) plus anyone already marked present/absent at that specific session despite having a *different* home cohort (`isHomeCohort: false`) — the make-up-guest tag a roster UI needs to distinguish the two without a second lookup.
- **Wired into the existing progress-attachment path**: `enrollmentService.attachProgressAndPayments` now also batches `getClassroomAttendanceSummaries` for every `driver_education` enrollment in the set whose `de_delivery_mode = 'classroom'` (one query for the whole batch, skipped entirely — zero extra queries — when none qualify) and attaches the result as `Enrollment.classroomAttendance`. `EnrollmentSubPanel.tsx` reads it to show "N/4 days attended" for a classroom enrollment, replacing the plain-text `manualCompletedHours` line that field still shows for **online** driver_education (which has no attendance concept — `manualCompletedHours` remains its only completion signal, untouched by this feature).
- **`joinCohort`** (`classroomService.ts`, `POST /api/v1/classroom/cohorts/:id/join`): what the student modal's enrollment flow calls when a student picks a cohort — writes exactly one `de_cohort_enrollments` row (a student has at most one home cohort, DB-`UNIQUE`-enforced on `enrollment_id`). Rejects a cancelled cohort, a cohort at capacity (`enrolledCount >= capacity`, live-computed), a non-`driver_education` enrollment, or an enrollment that already has a home cohort (409) — joining is a one-time, explicit action, never implicit or automatic.

Chosen over N separate per-session roster fetches — the shape the UI actually needs is "this cohort's full grid," matching this codebase's established batched-payload convention (`getCertificatesForEnrollments`, the students-list progress/fee/guardian attachment) over client-side per-item stitching; it also sidesteps calling `useQuery` in a loop, which would violate React's hooks rules the moment the "always exactly 4 sessions" assumption changed.

- **`joinCohort` made race-safe** (`classroomService.ts`): the original implementation read `enrolledCount` via `getCohortById` (a plain, unlocked `SELECT`) and only then inserted — two concurrent joins arriving at exactly-at-capacity could both read "1 spot left" and both insert, overfilling the cohort. FOR UPDATE` row-locks the cohort first, then `COUNT(*)` against `de_cohort_enrollments` is re-checked against that locked row before the insert, so a second concurrent caller blocks on the lock and sees the first caller's insert reflected in its own count. ## 15. Program-Aware Students Page (DE + BTW)

The Students list, its status computation, and its "add a BTW enrollment" flow were all built assuming every student is a BTW student — a `driver_education`-only student always fell into `computeStudentStatus`'s `!activeEnrollment` branch, showing "No Active Enrollment" and implying they were overdue to book a lesson, when they'd never touched BTW at all. Fixed by making status computation, the list's filter, and the enrollment-add flow all program-aware, reusing the Phase 3 (§14) attendance/completion data throughout rather than duplicating it.

- **DE enrollment batch-attach for the list** (`enrollmentService.getDeEnrollmentsBatch`, wired into `studentService.attachProgress`): a new batched query, structurally parallel to the existing `getDisplayDriverTrainingEnrollmentsBatch` but simpler — a student has **at most one** `driver_education` enrollment ever (`EnrollmentSubPanel`'s `canAddDriverEducation` gate), so no `DISTINCT ON` tie-break is needed. One query joins `enrollments → de_cohort_enrollments → de_cohorts` (for `cohortName`), then attaches `classroomAttendance` for the classroom-mode subset by calling `classroomAttendanceService.getClassroomAttendanceSummaries` — the exact same batched function `attachProgressAndPayments` (§14) already calls for the Enrollments tab, so this is the identical attendance/completion source, never a second calculation. Result is attached to every list-response `Student` as `deEnrollment: DeEnrollmentSummary | null` — one more batched call alongside the existing BTW one, zero N+1.
- **`hasCompletedInternalDe` on the detail read** (`studentService.getStudentById`): `true` when the student has a completed `driver_education` enrollment, derived **in-memory** from the `enrollments` array `getEnrollmentsForStudent` already fetches for the Enrollments tab — no extra query. (Deliberately not sourced from `hasCompletedInternalDriverEducation`, §14's single-purpose DB round trip for the BTW-discount check — that primitive exists for call sites that don't already have the enrollments list in memory; this one does.) List-response `Student` objects do not carry this field — only the single-student detail response does, since it's an eligibility signal for one specific student-record action (below), not a list-wide concern.
- **Parallel DE status track, not a case folded into `ComputedStatus`** (`frontend/src/utils/studentStatus.ts`): `ComputedStatus`/`computeStudentStatus` is built entirely around BTW's lesson-booking workflow (scheduled/ready-to-book/needs-attention/completed/inactive) — concepts with no meaning for DE's linear track (unassigned → enrolled → attending → complete). Cramming DE into that union would force every switch over it to grow dead branches. Instead: `DeComputedStatus`/`DeStatusInfo`/`computeDeStatus(deEnrollment)` is a new, separate pure function whose display text is a direct port of `EnrollmentSubPanel.tsx`'s existing DE progress-line wording (`"X/4 days attended"`, `"Completed - N/4 days attended"`, `"N hours logged"`, `"Completed - N hours"`) — reused strings, not a new calculation. A single dispatcher, `getDisplayStatus(student, programTab, btwStatus, deStatus)`, returns a `{ kind: 'btw' | 'de'; info }` discriminated union: the `de`/`btw` program tabs force their own track; `'all'` resolves to the **furthest-along program** — BTW status if `student.activeEnrollment` is present (the sequential DE-then-BTW model means a BTW enrollment implies DE is already behind the student), else DE status. (`ProgramTab` is a straight rename of the original `ProgramFilter` — same three values, same function body — once the page reframed program as a Notion-style tab rather than a filter chip, see below.)
- **A second, independent classification of the same `DeEnrollmentSummary`** — `classifyDeCard(deEnrollment): DeCardFilter`, `DeCardFilter = 'in_class' | 'unassigned' | 'completed' | 'awaiting_cert' | 'online_in_progress' | 'no_enrollment'` — buckets a DE enrollment for the Students page's DE-tab stat cards and status-filter chips (below), a different question from `computeDeStatus`'s "what text to show." Both read the same input, so they can never disagree about the underlying data, only about which independent question is being answered. `awaitingCertificate` (next bullet) takes priority over the plain `completed` bucket, since a completed-but-uncertified minor is actionable admin work that would otherwise be invisible inside a generic "Completed" count. `online_in_progress` is a real, counted bucket (reachable via the DE tab's "All" status chip) with no dedicated stat card — the page fixes exactly 4 DE cards, and neither "in a class" nor "unassigned" describes an online student.
- **DE awaiting-certificate flag, batch-attached alongside `deEnrollment`** (`enrollmentService.getDeEnrollmentsBatch`, extended): the same query gained one more `LEFT JOIN certificates` — mirroring `certificateService.getAwaitingCertificateWorklist`'s own eligibility check exactly (`completed = true AND certificates.id IS NULL`) — plus `e.completed_at` in its SELECT list, zero new queries. `studentService.attachProgress` computes `DeEnrollmentSummary.awaitingCertificate: boolean` in-memory per student, using the identical age-as-of-`completedAt` pattern `enrollmentService.attachProgressAndPayments`'s `wasMinorAtCompletion` already established (§13) — a student is only "awaiting" if they were a minor *as of completion*, not as of today. This is the batched source the DE tab's "Awaiting Cert" card/chip reads; the Students list never makes a second worklist call.
- **Program tabs, not a filter chip** (`Students.tsx`, `frontend/src/components/common/Tabs.tsx`): the three-value program selector (Behind-the-Wheel / Driver Education / All) was restructured from a row of `FilterButton` chips into a Notion-style underline `Tabs` component — a subtle weight+underline on the active tab, no pill/background fill. The reframing matters beyond the visual: switching tabs now swaps the stat-cards row, the status-filter chip set, AND the table/card columns together as one coherent presentation of that program's vocabulary, rather than a filter narrowing an always-BTW-shaped page (the prior design's gap — picking the DE chip left BTW's cards on screen and silently skipped status-filtering entirely, since none of BTW's 6 status values applied to a DE row). `hasBtw`/`hasDe` predicates are unchanged, still reading only the already-batch-attached `activeEnrollment`/`deEnrollment` fields — zero additional queries, and a student satisfying both still yields exactly one row per tab it matches. **"All" is the default tab, not "Behind-the-Wheel"**: the landing view must never hide a student behind an unchosen program — a DE-only or not-yet-enrolled student would otherwise vanish on first load. Dashboard's BTW-only deep-links (Needs Attention/Turning 18/etc.) explicitly force the Behind-the-Wheel tab active when they fire, since every value they carry is a BTW-only concept and the default is no longer BTW. On the All tab specifically, a student resolved to the DE track with genuinely no enrollment in either program is relabeled "Not Enrolled" (not "No DE Enrollment," which reads as though DE was expected and is missing) — a presentation-only override in `Students.tsx`, `computeDeStatus`'s own output is untouched. Each tab persists its own status-filter selection independently via its own `useSessionState` hook (`students-status-filter-btw` / `students-status-filter-de`, matching this codebase's existing one-hook-per-persisted-value convention — no JSON-blob-in-sessionStorage pattern was introduced for this).
- **Program column** (`Students.tsx` table + card views, present on every tab): a small badge showing `"DE"`, `"BTW"`, or `"DE·BTW"`, computed from the same `hasBtw`/`hasDe` predicates.
- **`StudentStatusBadge`/`StudentProgressBar` both extended to accept the DE track** alongside the existing BTW one, rather than a second badge/bar component: `StudentStatusBadge` now accepts either a plain BTW `StatusInfo` (every pre-existing caller, untouched) or the `getDisplayStatus` discriminated union, and renders DE with its own two-state palette (green once complete, neutral blue/info while in progress — DE has no "needs attention" urgency concept). `StudentProgressBar` accepts an optional `deStatus` prop; when present it renders the DE status text as a plain label instead of BTW's percent bar — DE's 4-day linear track doesn't fit a percent-complete bar the way BTW's hours/lessons do.
- **"Enroll in BTW"** (directional DE → BTW only, closing the gap §14 explicitly deferred: *"does not currently prompt for the permit... would need a second, atomic student+enrollment write, its own concern"*): a new atomic transactional endpoint, `POST /students/:id/enroll-in-btw` (`enrollmentService.enrollInBtw`), can touch up to **three writes** in ONE transaction — (a) the new `driver_training` enrollment, (b) an optional permit update on the student record, (c) an optional external-DE-completion stamp on the new enrollment (the transfer-student escape hatch — `externalDeCompleted`/`Date`/`Provider` only exist on a `driver_training` row, and none exists yet for a DE-only student at the moment this is called). Modeled on `createStudent`'s and `joinCohort`'s (§14) exact `BEGIN`/`COMMIT` shape: pre-checks (student exists, no existing active `driver_training` enrollment) run outside the transaction for a clean 404/400; a failure at any of the three writes rolls back all of them — verified by dedicated tests that fail the transaction mid-way (after the permit UPDATE, or after the enrollment INSERT) and assert no `COMMIT` ever appears in the client's call sequence. Eligibility (internal OR external DE completion) is **soft guidance only** — this function has no hard gate beyond the pre-existing driver_training-uniqueness rule; an admin can submit regardless.
  - **Frontend** (`EnrollmentSubPanel.tsx`): the old generic "Add driver training enrollment" text link is **replaced** (not supplemented) by a distinct "Behind-the-Wheel: Not enrolled" row, same visual weight as the enrollment cards above it, shown whenever the student has no active `driver_training` enrollment. Its "Enroll in BTW" button is enabled/prominent when `hasCompletedInternalDe` or the student's most recent `driver_training` enrollment's `externalDeCompleted` is true; otherwise shown with a "Requires DE completion" note and an inline "Record DE completed elsewhere" checkbox that reveals date/provider fields — checking it enables the button for *that* submission (the completion record travels with the same `enrollInBtw` call, not a separate action first). Permit fields are collected in the same confirm form, optional but prompted, prefilled from the student's current permit if any; they remain independently editable on the student record afterward either way. Directional only — no reverse "Enroll in DE" affordance exists anywhere. `hasCompletedInternalDe` is fetched via a new lazy `studentsApi.getById` query scoped to the Enrollments tab, since the list-response `student` prop `StudentModal` receives from `Students.tsx` doesn't carry it (list vs. detail attachment, per the `hasCompletedInternalDe` note above).
- **Bug fixed: no "Mark complete" action existed on the Students DE tab.** The list's row-action "Mark complete" button was (and still is, for BTW) gated on `isReadyToMarkComplete(student, lessons)` — purely a BTW lesson/hours-progress check, with no concept of DE completion at all. A DE student who finished all 4 curriculum days (classroom) or was ready per the Classroom Online tab's own judgment had no completion action anywhere on the Students page. Fixed by adding `isReadyToMarkDeComplete(deEnrollment)` (`studentActionEligibility.ts`) alongside the existing BTW-only function — it reads `deEnrollment.classroomAttendance?.isComplete` for classroom (the identical attendance-derived source the cohort roster and certificate worklist already use) and "active and not yet completed" for online (matching the Classroom Online tab's own ungated behavior), never a third calculation of DE completion. Wired into both card and table row-action blocks in `Students.tsx`, gated on `displayStatus.kind` so the BTW button can never appear on the DE tab or vice versa; the shared confirm step targets `student.deEnrollment.id` or `student.activeEnrollment.id` depending on which button triggered it, but still calls the exact same `completeEnrollmentMutation`/`enrollmentsApi.complete` path every other completion in the app uses — a convenience duplicate of an existing action, not a new completion mechanism. Live-verified: a classroom DE student at 4/4 attendance had zero actions before the fix, and after the fix the button appears, confirms, marks complete, and the student then correctly appears on the DE certificate worklist.
- **Bug fixed: "Mark contacted" silently 500'd on every call.** `students.last_contacted_at` was declared on the `Student` type and fully wired through `studentService.updateStudent`'s dynamic UPDATE builder and the Students page's `markContactedMutation` (`studentsApi.update(id, { lastContactedAt: new Date() })`), but no migration had ever actually created the column — every call hit a hard Postgres `42703` (`undefined_column`) error. Neither of the two plausible-looking causes held up on inspection: axios's default `JSON.stringify` + `Date.prototype.toJSON()` already correctly serializes the JS `Date` to an ISO string before the request leaves the browser, and `updateStudent`'s builder already correctly enumerated `last_contacted_at`. ## 16. Archive (Phase 4 of the Compliance Records Arc)

Completed students recede from the daily working views (the Students list, its tab counts, its filter chips) while staying fully retained, searchable, and retrievable — filing away, never deletion. §11108 requires 3-year retention, and years of completed students would otherwise balloon the active list with records nobody is actively managing.

- **Grain is the student, not the enrollment.** `archived_at`/`archived_by`/`archive_hash`/`archive_ledger_txid`/`archive_held`/`archive_hold_reason`/`archive_held_at`/`archive_held_by` all live on **`students`** (`027_add_student_archive.sql`) — the same grain the Students list itself renders. A person can hold a completed BTW enrollment and a completed DE enrollment at once (sequential DE→BTW is the normal path, §11/§14), so one seal per person, computed over **every** enrollment they have, is simpler than juggling independent per-enrollment seals for enrollments that both belong to one finished person. The **trigger**, however, evaluates per-enrollment (below) — a student is archive-eligible only when every enrollment they have independently clears its own program's at-rest rule; one active or incomplete-but-not-stalled enrollment blocks the whole student regardless of what their other enrollment looks like.
- **Eligibility is live-computed on every read, never a background sweep.** `studentService.getArchiveReadyWorklist` follows the exact pattern `dashboardService.getInstructorsWithExpiringLicenses` already established: fetch tenant settings/timezone, compute `todayStr` via `tenantToday`, compare fresh on every call, zero persisted "pending" state. Given this app's own history with silent automatic behavior (the DE completion display bug), sealing itself is always an explicit admin action from a worklist row — the same record-then-confirm shape the certificate worklist uses (§13) — never a cron write. There is no scheduled job anywhere in this feature.
- **BTW (`driver_training`) archives on permit expiration, falling back to inactivity.** `completed = true` is required first (an incomplete BTW enrollment past permit expiration is "stalled, may renew and return" — it stays in the active/needs-attention view, never surfaced here). If `students.learner_permit_expiration` (person-level, per §11/§14 — permit is never per-enrollment) is on file and has passed (`daysBetweenTenantDates(expiration, today) > 0`, the same primitive the license-expiry alert uses, just past-due instead of upcoming), the student is eligible. With no permit on file (e.g. an adult), the fallback is `tenant_settings.archive_inactivity_grace_days` (new column, `NOT NULL DEFAULT 90`, same `de_discount_amount`/`default_de_hours_required` tenant-configurable precedent, editable in `Settings.tsx`'s Training Defaults) days of no lesson activity since the enrollment's most recent lesson (a batched `MAX(date)` query across every completed candidate BTW enrollment at once, not N+1), or since `completed_at` if no lesson exists at all. New activity resets this automatically — the live query re-derives "most recent lesson" fresh every call, nothing to invalidate.
- **DE (`driver_education`, either delivery mode) archives on pure calendar-year rollover**, not a rolling 365-day clock: eligible once `tenantToday`'s year is later than `completed_at`'s year. Chosen because the sealed archive itself is grouped year → month (below) — calendar-year eligibility means a whole year's completed DE cohort seals and lands in that year's section together, one predictable rule, rather than two same-year completers (January vs. December) becoming eligible a full year apart under an anniversary rule. No permit logic — DE students may have no permit yet, correctly.
- **Manual overrides, all three explicit `students` UPDATEs**: "Archive early" (`POST /students/:id/archive`, `studentService.archiveStudent`) seals a completed record before the trigger fires — the same underlying function the worklist's per-row action and the bulk "Archive all eligible" action both call; it requires at least one completed enrollment (400 otherwise) but does **not** re-check the eligibility trigger itself (early archiving is allowed to precede the trigger by design). "Hold active" (`POST /students/:id/archive-hold`, requiring a `reason`) is a **permanent flag with no auto-expiry** — silently overriding deliberate admin knowledge on a timer is the same silent-automatic-behavior class this app has avoided elsewhere — kept visible via a dedicated `GET /students/archive-held` review list (the Archive page's "Held" tab) rather than a timed sweep. Clearing a hold (`POST /students/:id/archive-hold/clear`) only makes the student re-evaluable; it does not itself archive them. "Restore" (`POST /students/:id/restore`) flips `archived_at` back to `NULL`, confirm-guarded on the frontend, and deliberately leaves `archive_hash`/`archive_ledger_txid` in place — "this record was sealed once" is a historical fact that survives a restore, exactly mirroring `reopenEnrollment`'s own "never clears `completion_hash`" precedent (§6). If the student later re-completes and is re-archived, `archiveStudent` overwrites both with a fresh seal — the row holds only the latest state, an honest history of the record's most recent final form.
- **The seal hash** (`archiveStudent`): for every completed enrollment, collects `driver_training`'s per-lesson `{date, durationMinutes, instructorId}` facts (per-lesson, so a multi-instructor record — a student completing across more than one instructor — proves correctly) or `driver_education` classroom's `{cohortId, teacherInstructorId, attendedCurriculumDays}` (from `de_cohort_enrollments`/`de_attendance`, already-existing Phase 3 tables) — plus every certificate serial issued against that enrollment, `tenant_settings.license_number` (Phase 1, exactly as `023_add_license_number.sql`'s own comment anticipated), and the archive date. Hashed via Node's `crypto` module (SHA-256) — no `@bsv/sdk`, no wallet, no network call, identical forward-compat posture to `enrollments.completion_hash`/`certificates.completion_hash` (§12/§13, `docs/BLOCKCHAIN.md`). **No PII ever enters the payload** — IDs, dates, numbers, and enums only; names resolve from the DB by ID at display time, never stored in or alongside the hash. `archive_ledger_txid` is written nowhere beyond `NULL`, matching those same two columns' status exactly; the Archive page shows a plain "Hash recorded · not yet anchored" line per sealed record today, intended to become a real chain-verify affordance once `BSV_ENABLED` flips on and `LedgerService` grows a call for it (out of scope this phase).
- **Working-view exclusion is exactly one new predicate.** `studentService.getAllStudents` (`GET /students`) gained `AND archived_at IS NULL` on both its count and row queries — every downstream consumer (`attachProgress`, the Students page's `filteredAndSortedStudents`, its stat-card counts, its status-filter chips) already operates on whatever this function returns, so nothing else needed to change. `getStudentById`, `searchService.searchPeople`, `certificateService.getCertificateDetail`, and `transcriptService.generateWithdrawalTranscript` were confirmed (by direct inspection, not just intent) to already have **no** status filter of any kind on `students` — so an archived student's full record, certificate view/print, and transcript generation all continue to work completely unmodified. `searchPeople`'s result shape gained one additive field, `archivedAt`, purely so `UnifiedSearchResults.tsx` can render an "Archived" tag — the underlying query needed zero changes to keep finding them.
- **The Archive page** (`frontend/src/pages/Archive.tsx`, `/archive`, a plain nav entry with no feature flag — retention is core compliance, not optional, unlike Certificates/Classroom): three views under one Notion-style `Tabs` bar (§15's `common/Tabs`). "Ready to Archive" mirrors `Certificates.tsx`'s `WorklistRow` shell — each row states its reason concretely (permit expiry date / days inactive / DE completion year) with per-row Archive and Hold-active actions, plus a header "Archive all N eligible" bulk-confirm action (still one explicit click, never automatic). "Held" lists every currently-held student with its reason, so a permanent hold can be periodically reviewed and cleared rather than silently accumulating. "Sealed Archive" groups records year → month, newest year expanded by default (a plain toggle-per-year disclosure, no new dependency), each row showing its seal state and a confirm-guarded "Restore to active" action that reuses the exact expand-to-confirm-with-reason shell `StudentModal.tsx`'s own enrollment-reopen flow established.
- **Manual overrides also reachable from the student record itself**: `StudentModal.tsx`'s Progress tab gained an Archive section, visible once the student has at least one completed enrollment and hidden entirely once already archived — "Archive early" (confirm-guarded) and "Hold active" (required-reason prompt) when not held; "Clear hold" in place of both when already held. Both invalidate the `students` and `archive` query caches so the Archive page and Students list stay in sync with whatever was just done here.
- **New endpoints**: `GET /students/archive-worklist`, `GET /students/archive-held`, `GET /students/archive`, `POST /students/:id/archive`, `POST /students/:id/archive-hold`, `POST /students/:id/archive-hold/clear`, `POST /students/:id/restore`.

## 17. Payments: Add Payment Modal Redesign

This is manual/ledger tracking only — a real payment-processor integration (Stripe/Square) is an explicit FUTURE phase, out of scope here. Every method chip below records what an admin observed happened (cash handed over, a Venmo transfer received), never a live charge.

- **Bug fixed: every payment creation/update 500'd, unconditionally.** `paymentService.createPayment`'s INSERT and `updatePayment`'s UPDATE both referenced `payments.created_by`/`updated_by` — matching the `created_by`/`updated_by` audit-column pattern every other audited table (`students`, `lessons`) already has — but no migration had ever added these two columns to `payments`. Every `POST /payments` (and any `PUT` that set `updated_by`) hit a hard Postgres `42703` (`undefined_column`) error, regardless of `payment_method` value. The 27 payment rows present in dev/seed data were inserted directly by `database/seeds/001_budget_driving_school.sql`, bypassing this codepath entirely — which is how the bug went unnoticed; the API path had never actually worked. Fixed by `029_add_payment_audit_columns.sql`, adding both columns (`uuid`, FK to `users(id)` `ON DELETE SET NULL`, exactly matching the existing pattern) — zero backfill needed, since no row had ever been created through the buggy path to begin with. A full pass over both functions' column lists against the live schema confirmed these were the only two columns missing.
- **`payment_method`'s real values, and the frontend's prior mismatch.** The live CHECK constraint (`001_baseline.sql`) allows `bsv, mnee, stripe_card, paypal, cash, check, debit, credit` — but the old `PaymentModal.tsx` sent values like `credit_card`/`debit_card`/`bank_transfer`/`e_transfer`/`other`, none of which are valid; every payment submission would have failed the CHECK constraint on top of the missing-column bug above. The frontend `Payment`/`CreatePaymentInput` types (`frontend/src/types/index.ts`) previously declared an even-more-fictional set (`cash | card | stripe | paypal | bsv | mnee`) that matched neither the backend type nor the schema. Both frontend types are now a `PaymentMethod` union matching the real constraint exactly.
- **`venmo`/`zelle` added to the CHECK constraint — additive only.** `030_widen_payment_method_check.sql` drops and re-adds `payments_payment_method_check` with the same 8 existing values plus two new ones. Every existing value keeps its exact prior meaning; this only widens what's allowed, so no existing row or code path is affected. Chosen over reusing `paypal` for both, since a real payment record should say what actually happened — a Venmo transfer and a PayPal transfer are different apps, and collapsing them would misdescribe the ledger.
- **Method chip → `payment_method` mapping** (`PaymentModal.tsx`'s `METHOD_CHIPS`/`BLOCKCHAIN_METHOD_CHIPS`): Card → `credit`, Cash → `cash`, Venmo → `venmo`, Zelle → `zelle`, PayPal → `paypal`, Check → `check`, plus BSV → `bsv` / MNEE → `mnee` gated behind `enableBlockchainPayments`. **Card maps to `credit`, deliberately not `stripe_card`** — `stripe_card` means an actually-processed Stripe charge (the future phase this task explicitly excludes), while `credit`/`debit` exist specifically for a manually-recorded card tender; `credit` was picked over `debit` as the more common default for a hand-entered driving-school payment, with no separate debit/credit chip added since that distinction isn't asked for in the redesign brief.
- **BSV/MNEE gating reuses the real flag, not a placeholder.** Both chips read `useTenant().settings?.enableBlockchainPayments === true` — the exact flag `Sidebar.tsx`'s Treasury nav item already gates on, not a "Power Mode" toggle. Locked chips render muted with a dashed border and a small `Lock` icon (`lucide-react`), are `disabled` (unclickable, not just visually dimmed), and carry a `title` explaining why; unlocking them requires the tenant setting, not a special-case dev-only bypass.
- **`reference_number`** (`031_add_payment_reference_number.sql`, nullable `text`, no backfill): a free-text field for a manually-recorded payment's paper trail — a Square receipt number, a check number, the last 4 digits of a card. Never validated or parsed, purely an admin-facing lookup aid. Threaded through `createPayment`'s INSERT and `updatePayment`'s UPDATE (both `undefined`-guarded like every other optional field in those functions) and rendered as its own column in `PaymentHistoryModal.tsx`.
- **Smart amount pre-fill** (`PaymentModal.tsx`): the amount field defaults to the selected student's `paymentSummary.outstandingBalance` — a value the modal already fetched but had never used for the default — the moment a student is selected (pre-selected via the Payments list, or picked from the modal's own dropdown), fully editable, and re-applied whenever the student selection changes. An `amountTouched` flag (reset on every modal open and every student change) ensures the auto-fill never clobbers a value the admin has started editing themselves — it fires only up to the first manual edit.
- **Live running-balance preview**: `outstandingBalance - amount`, recomputed on every keystroke, rendered in a muted `bg-surface2` box directly above the confirm button. **Allowed to go negative, shown as a credit** (e.g. "$20.00 credit" in the success-green token), not floored at $0.00 — an overpayment is a real credit the student now holds toward a future charge, and silently flooring it would hide from the admin that they just recorded more than was owed. This is display-only arithmetic on an already-fetched value, not a second computation of the balance itself.
- **Double-submission guard** (item 5): the confirm button is `disabled` while `createMutation.isPending`, and `handleSubmit` itself early-returns if a mutation is already in flight — live-verified with a rapid double-click that only one `POST /payments` request ever fires and exactly one payment row is created.
- **Visual redesign**: rebuilt on `ModalShell` (this page's modals had drifted onto a hand-rolled backdrop+card, unlike `StudentModal`'s shared chrome) with the amount as a large centered display, Method/Date as two compact fields in one row, method as a `role="group"`/`aria-pressed` chip row (the same pattern `EnrollmentSubPanel.tsx`'s Classroom/Online delivery toggle already established) instead of a `<select>`, and one full-width primary `Button` with a "tap Confirm, or edit any field first" caption underneath — replacing the prior stack of equally-weighted labeled inputs.

## 18. Driver Education Pricing

Driver Education had NO pricing concept at all before this: no cost field ever populated on a DE enrollment, no tenant default, and — since `paymentService.createPayment` hard-required an active `driver_training` enrollment — a DE-only student could not have a payment recorded against them under any circumstance. This adds a real course-fee balance for DE, billed as one flat fee at enrollment (never per-lesson, unlike BTW).

- **Two new tenant defaults** (`032_add_de_course_fee_defaults.sql`): `default_de_classroom_cost`/`default_de_online_cost`, both `numeric(10,2) NOT NULL DEFAULT 150.00` — the same shape and placeholder-default posture as `default_lesson_cost`/`default_de_hours_required`. Classroom and online get independent defaults since they're different real-world offerings; $150 is a placeholder, editable per tenant in Settings' Training Defaults section (mirroring `default_lesson_cost`'s exact input pattern) immediately.
- **`enrollments.total_cost` is reused as-is for DE — no new column.** This column already existed (nullable, shared by every program on the one `enrollments` table) and was already BTW's own cost-override field; `enrollmentService.createEnrollment` now defaults it for a `driver_education` enrollment to the matching tenant setting (classroom vs. online) when not explicitly provided, exactly mirroring how `hoursRequired` is already defaulted differently per program in the same function. A negative `totalCost` 400s (`createEnrollment` and `updateEnrollment` both validate this) — the only new validation added. BTW's own `totalCost` handling is completely unaffected: still `null` unless explicitly set, never defaulted from a DE price.
- **Confirm-and-edit at every DE enrollment entry point**: `StudentModal.tsx`'s creation-time "Driver Education details" panel and `EnrollmentSubPanel.tsx`'s "add DE enrollment to an existing student" flow both gained a "Course fee" input, prefilled the moment a delivery mode is picked (`initialDeCost`/`draftDeCost` state, a `costTouched`-style guard so a manual edit is never clobbered by re-picking delivery mode — the identical pattern `SmartBookingForm`'s `defaultLessonCost` prefill already established) and fully editable before the enrollment is created. The backend still authoritatively defaults/validates the value server-side — the frontend prefill is never trusted as the final figure, matching BTW's own "prefill only" relationship to `lessons.cost`.
- **Bug found and fixed while wiring this up: payments could not attach to a DE-only student at all.** `paymentService.createPayment` unconditionally 400'd with "Student has no active driver_training enrollment" for anyone without one — a DE-only student's new course-fee balance would have been genuinely unpayable. Widened: when no active `driver_training` enrollment exists (and no `lessonId` is given — a lesson-linked payment still requires one, since a lesson only ever belongs to a `driver_training` enrollment), `createPayment` now falls back to the student's `driver_education` enrollment, preferring one with a genuine outstanding balance over just the most recent one. A student with neither program still 400s — this widens *what* a payment can attach to, not *whether* one is required.
- **List-level `Student.paymentSummary` now combines BOTH programs' balances.** Previously computed only from the active `driver_training` enrollment (`studentService.attachProgress`) — a DE-only student always got `paymentSummary: undefined` regardless of a real DE balance, which would have made the new DE cost invisible on the Payments page and in the Add Payment modal's pre-fill (§17). Fixed via a new `combinePaymentSummaries` helper: each program's own total is computed by the identical `computePaymentSummary` the Enrollments tab already uses per-enrollment (`enrollmentService.attachProgressAndPayments`) — never a second/different balance calculation — then summed. `'unknown'`/`null` only when *neither* program has a computable total; a computable DE balance alongside an "unknown" BTW one (or vice versa) still yields a real combined total, since "not computable yet" contributes nothing to the sum rather than blocking it. The batched payments query in `attachProgress` was widened to look up amounts for both the BTW and DE enrollment ids in one query (not two), since a payment can now attach to either.
- **The BTW discount is completely unaffected.** `hasCompletedInternalDriverEducation` and `lessonService.ts`'s discount-application logic (§11) were not touched in any way (confirmed via a zero-diff check on both) — the discount still applies only to a BTW lesson's cost for a student with a completed internal DE enrollment, and never discounts the DE course fee itself.
- **Live-verified end-to-end**: a newly-created DE-only classroom student got `total_cost: 150` on their DE enrollment and `paymentSummary.outstandingBalance: 150` at the list level; the Add Payment modal for that student pre-filled $150.00; recording a $150 payment attached it to the DE enrollment (not a nonexistent BTW one) and dropped their balance to $0.00 with `paymentStatus: 'paid'`, all confirmed via the real running UI (not just the API) with the Payments page's own "Outstanding" summary card reflecting the change; a student with both a BTW and a DE balance showed both correctly summed into one `paymentSummary`.

## 20. Guardian-Staged DE Creation: Three Bugs From One Real Walkthrough

A real create-a-DE-student walkthrough (student "Sami Corona") surfaced three bugs in one session, the first two turning out to be one root cause plus its direct symptom.

- **Bug found and fixed: `initialEnrollment` was read from the wrong location on the guardian-staging create path.** `studentService.createStudentWithGuardian`'s `CreateStudentWithGuardianInput` type declared `initialEnrollment` as a **sibling** field of `student` (`{ student, guardians, initialEnrollment? }`), and the function read it via `input.initialEnrollment`. But `StudentModal.tsx`'s `submitWithStagedGuardians` builds one `CreateStudentInput` object (which already carries `initialEnrollment` as one of its own fields, matching the plain-create path's shape) and sends it whole as `student: submitData` — so `initialEnrollment` actually arrives **nested inside `student`**, never at the top level `input.initialEnrollment` was reading from. Every guardian-staged (minor) Driver Education creation silently fell through to the `driver_training` default, producing a real Behind-the-Wheel enrollment for a student who selected Driver Education. Confirmed via `git log -S`: this was never a regression from working code — the plain `createStudent`/`createStudentWithGuardian` pair were added together in one commit with genuinely different parameter shapes (`createStudent` takes `initialEnrollment` as a true separate 3rd function argument; `createStudentWithGuardian` folded it into one `input` object, but at the wrong nesting level relative to where the frontend actually puts it) — a real contract mismatch between frontend and backend, not a later break. Fixed by moving the type declaration and the read (`data.initialEnrollment`, where `data = input.student`) to match the frontend's actual shape.
- **Bug 2 confirmed as a pure downstream symptom of bug 1, not independent.** With bug 1 live, a guardian-staged DE student ends up with a `driver_training` enrollment and no `driver_education` enrollment at all. `StudentModal.tsx`'s `joinCohortAfterCreateMutation` looks up the new student's enrollments and searches for `programType === 'driver_education'` — finding none, it throws a plain `Error('driver_education enrollment not found for the newly created student')`, a non-axios error with no `.response.data.error`, so the UI's fallback text renders: "The student was created, but could not be enrolled in the cohort - assign them from the Classroom page instead." ## 21. Payments Sort-by-Date + Month-over-Month Trend (and a Tenant-Time Bug Fix on Students.tsx)

Two additions to the Payments page, plus a pre-existing tenant-timezone bug found and fixed on Students.tsx along the way.

- **New `getMonthBoundaries(dateStr, monthOffset)` helper** (`frontend/src/utils/timeFormat.ts`), alongside `addCalendarDays`. Pure calendar-month arithmetic on an already-resolved date string - given `dateStr` and an offset in months (0 = the month `dateStr` falls in, -1 = previous month, -12 = same month a year earlier), returns `{ start, end }` as `YYYY-MM-DD`. Same "safe client-side because the input is already tenant-resolved" reasoning as `addCalendarDays` - always call it with `tenantNow.today`, never a browser-derived date.
- **Sort by payment date** (Payments.tsx): `SortOption` gained `'date_newest'`/`'date_oldest'`, added to the existing sort `<select>` alongside name/balance. The table renders one row per **student**, not per payment, so "sort by payment date" is defined as: sort students by their most recent payment's `createdAt` (via a new `getLastPaymentCreatedAt` helper) - the same "derive one comparable date per student from a related records array, unmatched students go to the end" shape as this file's own pre-existing `'last_lesson'` sort on Students.tsx.
- **Month-over-month trend on "Collected This Month"**: the card now shows a small comparison line below the main figure - `TrendingUp` icon (rotated 180° when the diff is negative) plus `±$diff vs last month ($lastMonthTotal)`, in success/danger token colors depending on sign. This is the exact visual pattern Students.tsx's "New This Month" card already used (see below) - reused as-is, not reinvented. Last month's collected total is computed via `getMonthBoundaries(tenantNow.today, -1)`, filtered the same way the existing this-month figure already was (`status === 'confirmed'`, date string in range).
- **Pre-existing bug found and fixed: Students.tsx's own "New This Month" trend computed its month boundaries via browser-local `new Date()`.** The `stats` `useMemo` built `monthStart`/`lastMonthStart`/`lastMonthEnd`/`lastYearSameMonthStart`/`lastYearSameMonthEnd` via `new Date(now.getFullYear(), now.getMonth(), ...)` - the same browser-vs-tenant-timezone bug class this app has fixed multiple times elsewhere (§7). A browser sitting in a timezone far ahead of the tenant's, near a month boundary, could count or exclude a student on the wrong side of "this month" relative to the tenant's own clock. Fixed in the same pass as the Payments additions (not shipped separately) by resolving all three boundaries from `tenantNow.today` via `getMonthBoundaries`, and comparing against `student.createdAt`/`updatedAt` as date-prefix strings (`String(x).split('T')[0]`) rather than live `Date` objects - matching the string-comparison convention `tenantNow.monthBoundaries` usage already follows elsewhere in this file. `stats` returns all-zero when `tenantNow` is not yet hydrated, rather than falling back to a browser-derived guess.
- **Live-verified against the real dev database** (tenant `America/Los_Angeles`, `tenantNow.today` = 2026-09-09 at verification time): Payments' Collected This Month showed $250.00 with a correctly-computed `-$1365.00 vs last month ($1615.00)` (September's $250 vs August's real $1615 in confirmed payments), down-arrow rendering in both themes; sort-by-date-newest/oldest both correctly reordered the table by most-recent-payment. Students' own trend card, after the fix, showed `6 / vs last month (10) / -4`, cross-checked directly against `GET /students` (6 real students created in September 2026, 10 in August 2026) - confirming no regression, just now tenant-time-correct.
- **Hostile-clock regression coverage**: `Payments.test.tsx` and a new `Students.hostileClock.test.tsx` both set `process.env.TZ = 'Pacific/Kiritimati'` (UTC+14, far ahead of the mocked tenant's `America/Los_Angeles`) near a real month boundary and assert the rendered trend numbers match the tenant-resolved boundary, not what a browser in that hostile zone would compute.

## 22. Health-Audit Fix-Up, Pass 1: Three Live Bugs

Three independently-confirmed, live bugs from a full codebase health audit, fixed in this pass. Unrelated to each other - shipped as three separate commits.

### `notification_queue` had no migration anywhere in the repo

`lessonService.ts` INSERTs into `notification_queue` on every lesson booking (confirmation + 24h/1h reminders, student and instructor) and on cancellation (2 more inserts plus an UPDATE) - wrapped in try/catch, logged as a non-blocking warn, so booking itself never failed, but **every** booking confirmation/reminder had silently never been queued in this app's entire history. Separately, `GET /notifications/history` and `GET /notifications/queue` (backing the live, nav-reachable `/notification-history` page for owner/admin/staff) hard-500'd on every call.

- **`033_add_notification_queue.sql`**: column set derived from reading every actual INSERT/SELECT/UPDATE across `lessonService.ts`, the old `routes/notifications.ts`, and `notificationProcessor.ts` - not a guessed minimal schema. `id`, `tenant_id`, `lesson_id`, `notification_type` (CHECK: `booking_confirmation`/`reminder_24h`/`reminder_1h`/`cancellation`), `recipient_email`, `recipient_type` (CHECK: `student`/`instructor`), `scheduled_send_time`, `status` (CHECK: `pending`/`sent`/`failed`/`cancelled`, default `pending`), `sent_at`, `attempt_count` (default 0), `last_attempt_at`, `error_message`, `created_at`/`updated_at`. FKs to `tenants`/`lessons` (`ON DELETE CASCADE`), modeled on `fee_flags`' shape.
- **A second, previously-hidden bug surfaced once the table existed**: the history/queue SQL referenced `lessons.lesson_date`, a column that has never existed (the real column is `lessons.date`) - this went uncaught for as long as `notification_queue` itself didn't exist, since the query never got far enough to hit it. Fixed inline (`l.date AS lesson_date`) as part of restoring the same query, not a separate bug.
- **Moved the raw SQL out of `routes/notifications.ts`** into a new `notificationQueueService.ts` (service-layer DB access, matching every other domain) plus a new `notificationQueueController.ts` (routes → controller → service, matching `dashboardController.ts`'s shape) - the route file is now pure routing. Replaced `console.error`/`console.log` with `createLogger('NotificationQueueController')`. Kept as a **separate** service from the existing `notificationService.ts`, which already correctly documents itself as being about the `notifications` table (in-app alert dismissal), not `notification_queue` (the outbound email pipeline) - conflating the two would have blurred a distinction the codebase already draws carefully.
- **A necessary companion fix to actually complete this bug's own live-verification**: `frontend/src/api/notifications.ts` used its own bare `axios.create()` instance with a hardcoded fallback tenant ID (`'test-tenant-123'`) and **no auth-token interceptor at all** - every request from `/notification-history` went out with no `Authorization` header, so the page 401'd for any real logged-in user regardless of the table existing. Switched to the shared `apiClient` (matching every other `frontend/src/api/*` module), which is what CLAUDE.md's "frontend data fetching goes through `frontend/src/api/*` modules" convention already specifies. This wasn't one of the three originally-scoped bugs, but without it the task's own required live-reproduction step (visit `/notification-history`, confirm it loads with real data) could not be completed.

The manual `POST /notifications/process` trigger works end-to-end (confirmed live) but currently processes zero rows because of this second mismatch - flagged, not fixed, pending a decision on whether to invest in wiring the cron up for real.
